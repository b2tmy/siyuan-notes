# C/C++ 逆向

# C/C++ 逆向

C/C++ 逆向的核心是从编译结果恢复数据布局、控制结构、函数接口、对象生命周期和类型关系。编译器会删除变量名、合并表达式、内联函数并重排控制流，因此目标通常不是逐行还原源码，而是建立一个能够解释程序行为的等价模型。

同一份源码在不同编译器、版本、优化级别、架构和 ABI 下会产生不同代码。分析时应把“C/C++ 语言语义”“ABI 约定”和“当前编译器实现”分开，避免把某个样本中的模式当成永久规则。

## 0x00 从源码语义到机器代码

```text
C/C++ 源码
 -> 预处理
 -> 编译与优化
 -> 汇编/目标文件
 -> 链接
 -> PE 映像
 -> Loader 与运行库初始化
 -> 进程中的最终执行代码
```

逆向面对的是最后几层的产物。宏、typedef、注释、局部变量名和大部分模板语义已经消失；剩下的是指令、常量、地址、调用、运行库、异常元数据和可能保留的 RTTI/符号。

## 0x01 C 基本类型与宽度

恢复变量类型时，先确定访问宽度，再判断符号性和用途。char、short、int、long、long long、指针和 size_t 的宽度受平台和 ABI 影响；Windows x64 仍采用 LLP64，long 为 32 位，指针和 size_t 为 64 位。

```text
Windows x86：pointer=4, long=4, size_t=4
Windows x64：pointer=8, long=4, size_t=8

不要看到 8 字节变量就自动命名为 long；它更可能是指针、size_t、uint64_t 或 double。
```

- MOVZX：零扩展，常提示无符号小整数。
- MOVSX/MOVSXD：符号扩展，常提示有符号整数。
- 32 位寄存器写入：在 x64 上通常清零高 32 位。
- 浮点指令：XMM 中的位模式不能直接按普通整数解释。
- 位掩码：可能是标志集合、枚举或结构中的位域。

## 0x02 if、else 与短路求值

if/else 通常表现为比较、条件跳转和汇合块。逻辑与、逻辑或常使用短路求值，因此右侧表达式只在需要时执行。优化器也可能使用 SETcc、CMOVcc 或算术替代显式跳转。

```asm
if (a && check(b)) success();

候选控制流：
test a, a
je failed
call check
test eax, eax
je failed
call success
```

恢复条件时必须确认比较的有符号性、操作数宽度和跳转方向。反编译器生成的复合布尔表达式需要回到基本块核对。

## 0x03 循环结构

- for：初始化、条件、循环体和增量通常能够分离。
- while：先判断条件，再执行循环体。
- do-while：循环体至少执行一次，条件位于尾部。
- 范围循环：可能展开为 begin/end 指针或迭代器比较。
- 优化循环：可能展开、向量化、合并或完全消除。

```text
for (size_t i=0; i<count; ++i) sum += array[i];

典型线索：
index 初始化为 0
比较 index 与 count
访问 base + index * element_size
累加结果
index 增加并回跳
```

循环恢复要记录四项：初始值、终止条件、步进方式和每轮副作用。越界、整数溢出和符号转换通常隐藏在这些位置。

## 0x04 switch 与枚举

switch 可能编译为比较链、二分决策或跳转表。连续 case 较多时常出现范围检查和间接跳转；稀疏 case 可能仍使用比较链。枚举在机器层通常只是整数，其语义来自比较常量和使用位置。

```asm
cmp eax, MAX_CASE
ja default
lea rcx, jump_table
movsxd rax, dword ptr [rcx+rax*4]
add rax, rcx
jmp rax
```

## 0x05 数组与指针运算

数组访问的核心是基址、索引和元素大小。编译器把 array[i] 转换为 base + i * sizeof(element)。指针递增也按指向类型的大小缩放。

```text
int *p;       p[i]   -> base + i*4
uint64_t *p;  p[i]   -> base + i*8
Record *p;    p[i]   -> base + i*sizeof(Record)
```

- 固定 scale 1/2/4/8 可直接从寻址模式观察。
- 复杂结构大小可能通过 IMUL 或 LEA 组合计算。
- 二维数组需要结合行宽和连续布局恢复。
- 指针差值的单位是元素，不一定是字节。

## 0x06 字符串与缓冲区

C 字符串依靠终止零表示长度，C++ 字符串对象通常保存长度和容量。分析复制和格式化时，应区分字符数量、字节数量、目标容量和是否包含终止符。

- strlen 返回字符数，不包含终止零。
- sizeof 数组在编译期可得整个数组大小，指针则只得到指针宽度。
- memcpy 使用字节长度，不处理字符串终止。
- strncpy 等函数的终止行为容易被误解，应结合实际参数。
- 宽字符串在 Windows 中常使用 UTF-16LE，字符单元为 2 字节。

## 0x07 结构体布局

结构体字段按声明顺序排列，但编译器会根据成员对齐插入填充，结构体总大小通常向最大对齐要求取整。#pragma pack、编译选项和 ABI 会改变布局。

```c
struct Example {
    uint8_t  flag;    // +0x00
    // padding          +0x01..0x03
    uint32_t count;   // +0x04
    void    *buffer;  // +0x08 on x64
};                   // sizeof = 0x10
```

- 相同基址加固定偏移：字段访问候选。
- 访问宽度：推测字段大小。
- 写入顺序：构造、解析或初始化函数常连续设置字段。
- 字段传参：可帮助确认指针、长度、句柄或回调类型。
- 多个函数共享同一偏移集合：说明它们操作同一对象类型。

### 7.1 位域与联合体

位域通常表现为掩码、移位和读改写；联合体让多个字段共享同一地址，因此同一偏移可能按不同类型访问。遇到不一致类型时，不要立即认为反编译器错误，也可能是联合体、类型重解释或协议复用。

## 0x08 内存所有权与生命周期

恢复指针类型后，还需要回答谁分配、谁释放、指针能使用到什么时候。悬空指针、重复释放和所有权转移都与生命周期有关。

```text
创建/分配
 -> 初始化
 -> 保存到局部/对象/全局
 -> 读取或修改
 -> 转移所有权或增加引用
 -> 析构/释放
 -> 指针失效
```

- 栈对象：作用域结束时通常自动销毁。
- 堆对象：通过 malloc/free、new/delete 或自定义分配器管理。
- 全局/静态对象：初始化和析构可能发生在 main 前后。
- 引用计数对象：最后一个引用释放时销毁。
- 借用指针：不拥有对象，生命周期依赖其他所有者。

## 0x09 malloc/free 与 new/delete

malloc/free 管理原始内存，不自动调用构造和析构；new/delete 通常结合内存分配与对象生命周期。编译结果中 new 可能表现为 operator new 调用、空指针检查和构造函数调用，delete 则可能先调用析构函数再释放内存。

```text
T *p = new T(arg);

候选代码形态：
call operator new
test rax, rax
je allocation_failed
mov rcx, rax
mov rdx, arg
call T::T

若构造抛异常，还可能存在释放已分配内存的清理路径。
```

## 0x0A C++ 对象与 this 指针

非静态成员函数隐含 this 指针。Windows x64 中它通常作为第一个参数位于 RCX；x86 MSVC 的 thiscall 常使用 ECX。对象字段表现为 [this+offset]。

```asm
void Counter::add(int value) { count += value; }

Windows x64 候选：
; RCX = this, EDX = value
add dword ptr [rcx+count_offset], edx
ret
```

识别 this 的关键不是寄存器名称，而是同一指针在函数内被反复作为稳定基址，并在多个相关成员函数中访问相同字段偏移。

## 0x0B 构造函数

构造函数负责建立对象初始状态。带虚函数的类通常在构造期间写入 vftable 指针；派生类构造前会先构造基类和成员对象。不同阶段可能多次写入不同 vftable。

```text
Derived::Derived()
 -> Base::Base()
 -> Member::Member()
 -> 写入 Derived vftable
 -> 初始化 Derived 字段
 -> 构造函数体
```

- 连续零初始化或常量写入：字段默认值。
- 对子对象地址 this+offset 调用构造函数：成员对象或基类子对象。
- 写入只读区中的函数指针表地址：vftable 候选。
- 异常清理路径：部分成员构造成功后需要逆序销毁。

## 0x0C 析构函数

析构函数通常按构造相反顺序释放资源：先执行派生类析构逻辑，再析构成员和基类。多态类可能有普通析构、完整对象析构和 deleting destructor 等编译器生成变体。

- 恢复 vftable：析构期间可能把对象切换回基类视角。
- 释放成员：字符串、容器、句柄和堆指针。
- 条件 delete：根据标志决定是否释放对象内存。
- 异常安全：清理路径可能与正常析构共享代码。

## 0x0D 虚函数表

多态对象通常含有一个或多个 vftable 指针。虚调用表现为先从对象读取表地址，再按固定槽位读取函数指针并间接调用。

```asm
mov rax, [rcx]          ; vftable
call qword ptr [rax+20h]   ; 调用某个虚函数槽位
```

- vftable 常位于只读数据区，表项指向可执行代码。
- 构造和析构函数是寻找 vftable 写入点的重要入口。
- 相同槽位在派生类 vftable 中可能指向覆盖后的函数。
- 纯虚函数槽位可能指向运行库的纯虚调用处理函数。

表项顺序属于 ABI 和编译器实现细节。恢复类接口时，应结合多个 vftable、调用点和 RTTI，而不是仅按槽位猜测源代码声明顺序。

## 0x0E 单继承

简单单继承中，基类子对象通常位于派生对象起始位置，派生类字段追加在后。派生类可以复用或替换 vftable 槽位。对象指针在基类和派生类视角下可能数值相同，但可见字段和虚调用目标不同。

## 0x0F 多重继承与 this 调整

多重继承会在一个完整对象内形成多个基类子对象，可能存在多个 vftable 指针。调用次要基类的函数时，需要把完整对象指针调整到对应子对象；编译器可能生成 this-adjusting thunk。

```text
完整对象地址 = 0x1000
BaseA 子对象   = 0x1000
BaseB 子对象   = 0x1020

调用 BaseB 方法前：this += 0x20
Thunk 返回 Derived 视角时：this -= 0x20
```

- 同一对象不同入口函数使用不同固定偏移。
- 短小函数只调整 RCX/ECX 后跳转：thunk 候选。
- 多个 vftable 分布在对象不同偏移。
- 析构函数可能分别处理完整对象和基类子对象。

## 0x10 虚继承

虚继承需要在运行时定位共享虚基类，MSVC 常通过 vbptr/vbtable 和偏移计算完成。此时基类位置不一定是编译期固定常量，字段访问前可能先读取表项再调整 this。

看到额外的表指针、表项偏移和多次 this 调整时，应保留“虚基类候选”而不是立即强制套用普通多重继承结构。

## 0x11 RTTI

启用 RTTI 时，编译器会生成支持 typeid、dynamic_cast 和类层次描述的数据。MSVC 多态类的 vftable 附近常能找到与类型描述和继承层次相关的结构。RTTI 可以显著帮助恢复类名与继承，但可能被关闭、剥离、混淆或部分保留。

- TypeDescriptor：可能包含修饰后的类名。
- Complete Object Locator：关联 vftable 与类层次信息。
- Class Hierarchy Descriptor：描述继承关系特征。
- Base Class Descriptor：描述基类及对象内偏移关系。

RTTI 中的名称是强线索，但仍需检查 vftable、构造函数和字段访问是否与继承模型一致。

## 0x12 名称修饰与符号

C++ 支持重载、命名空间、类和模板，因此链接符号需要编码更多信息。MSVC、Itanium ABI 等使用不同名称修饰规则。导出名称或残留符号可恢复函数名、类、参数和模板实例，但反修饰结果仍需与调用约定和实际访问核对。

## 0x13 异常处理

C++ 异常需要记录可抛出区域、清理动作、catch 匹配和栈展开。Windows x64 非叶函数通常具有 pdata/xdata 展开信息；语言相关处理数据用于描述 C++ 清理和处理器。

```text
try {
    Resource r;
    may_throw();
} catch (const Error &e) {
    handle(e);
}

异常路径必须：
- 销毁已构造对象
- 恢复非易失寄存器和 RSP
- 匹配处理器
- 进入 catch 或继续展开
```

- 清理函数可能看似无调用者，但由异常元数据引用。
- 大量析构调用可能属于异常清理，而非普通业务路径。
- catch(...) 与 SEH 异常的关系受编译选项影响。
- x64 函数边界和调用栈恢复可借助 RUNTIME_FUNCTION 和 unwind 信息。

## 0x14 模板与内联

模板在编译期实例化，不保留“模板源码”这一层。不同类型产生不同实例，链接器可能合并相同代码；小模板函数又常被内联，最终表现为普通指令序列。

- 名称中残留模板参数是直接线索。
- 相似函数结构但元素宽度不同可能来自不同模板实例。
- 容器操作内联后会与业务逻辑混合。
- LTO 和优化会让模板边界更加模糊。

## 0x15 std::string

std::string 的对象布局取决于标准库实现、版本、架构和调试模式。常见实现包含指针或内联缓冲区、长度和容量，并可能使用 Small String Optimization。不要写死某一版本偏移。

- 短字符串可能直接存放在对象内部。
- 长字符串通常由堆缓冲区保存。
- size 与 capacity 的比较常决定是否重新分配。
- data/c_str 返回的地址不一定等于对象地址。
- 析构只在使用外部缓冲区时释放堆内存。

识别 string 时，应结合构造、赋值、reserve、append、析构和字符数据引用，而不是只看三个指针或某个固定大小。

## 0x16 std::vector

许多实现中的 vector 可以抽象为 begin、end 和 capacity_end 三个指针，但具体布局仍依赖标准库和配置。元素数量通常为 (end-begin)/sizeof(T)。

```text
begin        -> 第一个元素
end          -> 最后一个已构造元素之后
capacity_end -> 已分配空间末尾

size     = (end - begin) / sizeof(T)
capacity = (capacity_end - begin) / sizeof(T)
```

- push_back 容量不足时会分配更大缓冲区并搬移元素。
- 元素不是平凡类型时，扩容会调用移动/拷贝构造和析构。
- 遍历通常表现为当前指针与 end 比较。
- vector<bool> 是特殊压缩实现，不能按普通 bool 数组理解。

## 0x17 map、unordered_map 与节点容器

树形 map/set 常由节点、父子指针、颜色和哨兵构成；unordered_map 常由桶数组和节点链组织。实现差异很大，优先从比较函数、哈希函数、节点分配和迭代逻辑恢复。

## 0x18 智能指针

- unique_ptr：独占所有权，移动后源对象通常置空。
- shared_ptr：对象指针与控制块，控制块保存强/弱引用计数和删除器。
- weak_ptr：不增加强引用，用于观察 shared_ptr 管理对象。
- 自定义删除器：可能改变对象大小和销毁调用链。

看到原子递减、引用计数归零后调用虚拟销毁或删除器，通常是 shared_ptr 或自定义引用计数对象候选。确认时要区分对象本身与控制块。

## 0x19 Lambda、回调与闭包

捕获型 lambda 通常编译为匿名闭包对象，捕获变量成为字段，operator() 成为成员函数。无捕获 lambda 可能转换为普通函数指针。

```text
[ctx, limit](int value) { return ctx->check(value, limit); }

候选闭包布局：
+0x00 ctx 指针
+0x08 limit
operator()(this, value)
```

回调注册时看到一块小对象和函数指针共同传递，可能是闭包、std::function 或框架委托。应追踪捕获字段和最终间接调用。

## 0x1A std::function 与类型擦除

std::function 可以保存不同种类的可调用对象，并通过类型擦除统一调用。实现可能包含小对象缓冲区、管理函数和调用函数指针，因此间接调用链比普通函数指针更复杂。

## 0x1B 静态对象与全局构造

全局和函数内静态 C++ 对象需要初始化和析构登记。程序入口前可能存在构造函数表调用；函数内静态对象可能使用线程安全初始化保护。

- 构造列表：运行库在 main 前调用。
- atexit/onexit：登记退出时清理函数。
- 初始化保护：判断静态对象是否已经构造。
- 失败清理：构造抛异常时保护状态需要恢复。

## 0x1C 拷贝、移动与返回值优化

拷贝构造读取源对象并建立独立状态；移动构造转移资源并让源对象进入可析构状态。优化器可能执行 RVO/NRVO，直接在调用者提供的返回缓冲区构造对象，使源代码中的临时对象和拷贝完全消失。

## 0x1D 函数重载与默认参数

重载在机器层表现为不同符号或不同函数；默认参数由调用者在编译期填入，被调函数通常不知道参数是否来自默认值。因此不能只从被调函数判断源码是否声明了默认参数。

## 0x1E const、volatile 与引用

const 主要是编译期类型约束，优化后的机器码未必保留明显标记。引用通常按指针传递，但语言层保证和指针不同。volatile 会影响编译器访问优化，却不等同于线程同步或原子操作。

## 0x1F 原子操作与锁

std::atomic 可能编译为 lock 前缀指令、交换、比较交换或平台内在函数。内存序语义并不总能只从单条指令恢复，需要结合周围屏障、平台内存模型和使用位置分析。

## 0x20 编译优化下的 C/C++ 模式

- 内联：函数边界消失，多个调用点各自包含逻辑。
- 常量传播：变量和条件被折叠。
- 死代码删除：源码分支可能完全不存在。
- 循环展开/向量化：一个源码循环变成多元素并行处理。
- 尾调用：CALL/RET 变成 JMP。
- 去虚拟化：已知对象类型时，虚调用变成直接调用。
- 相同代码折叠：不同源码函数共享同一实现地址。

恢复的伪代码应追求行为等价，而不是外观与原源码相同。遇到难以恢复的局部变量时，优先解释输入、输出、状态和边界。

## 0x21 编译器和标准库差异

MSVC、GCC 和 Clang 在名称修饰、异常、RTTI、对象布局细节、标准库实现和优化策略上存在差异。MSVC 的 STL 还会因工具集版本、调试迭代器和编译选项改变布局。

- 先识别编译器和运行库候选。
- 类型布局以目标 ABI 和实际访问为准。
- 不要把 libstdc++ 的容器布局套到 MSVC STL。
- 不要把 Debug 构建模式套到 Release 样本。
- 跨版本脚本应通过特征和符号验证，而不是只写固定偏移。

## 0x22 类恢复流程

```text
1. 找构造/析构与 vftable 写入
2. 汇总所有 [this+offset] 访问
3. 按宽度建立候选字段
4. 标记成员对象和基类子对象
5. 枚举 vftable 槽位与调用点
6. 结合 RTTI 恢复继承候选
7. 动态观察对象创建、虚调用和销毁
8. 修正结构、函数原型和命名
```

类结构应逐步建立。先定义已确认字段，其余保留 padding 或 field_xx；过早创建完整结构会让错误类型传播到大量函数。

## 0x23 动态验证对象布局

- 在构造函数入口记录 this 地址。
- 对 vftable 指针写入设置断点，观察构造阶段。
- 在成员函数中核对 this 和字段偏移。
- 对关键字段设置硬件写入断点。
- 观察析构顺序和释放函数。
- 创建多个对象，确认字段偏移和调用模式稳定。

## 0x24 可复现实验

```cpp
class Base {
public:
    virtual ~Base() = default;
    virtual int calc(int x) = 0;
};

class Derived : public Base {
    std::string name;
    std::vector<int> values;
public:
    Derived(std::string n);
    int calc(int x) override;
};
```

- 分别编译 x86/x64、Debug/Release 版本。
- 记录对象大小、vftable、构造和析构调用。
- 观察 std::string 短字符串和长字符串的差异。
- 观察 vector 空、未扩容和扩容后的布局。
- 比较虚调用和优化后的去虚拟化调用。
- 启用/关闭 RTTI 和异常后比较二进制变化。

## 0x25 常见错误

- 把一个固定偏移直接命名为完整业务字段。
- 把 vftable 中每个地址都当成普通成员函数。
- 忽略构造期间 vftable 多次切换。
- 把 deleting destructor 当成普通析构函数。
- 按某篇文章的固定偏移识别所有 STL 对象。
- 看到三个指针就断言是 vector。
- 把异常清理函数当作正常业务调用。
- 强行恢复原始源码，而忽略优化后的等价语义。
- 不区分编译器、标准库、架构和构建模式。

## 0x28 总结

C/C++ 逆向可以沿三条主线推进：控制流恢复源码级结构，数据布局恢复数组、结构体和对象，生命周期恢复构造、所有权和析构。C++ 在此基础上增加虚函数、继承、RTTI、异常、模板和标准库。分析时先确认 ABI 和编译环境，再从真实访问和调用建立候选类型，最后用动态对象和多处调用验证，才能得到稳定且可维护的程序模型。
