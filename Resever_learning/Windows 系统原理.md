# Windows 系统原理

逆向 Windows 程序时，文件结构只解释程序如何被描述，系统原理才解释程序如何被创建、装载、调度、访问内存、打开资源和处理异常。本章围绕用户态分析最常遇到的系统对象展开：进程、线程、虚拟内存、句柄、访问令牌、DLL Loader、PEB/TEB、异常分发和系统调用。

## 0x00 Windows 执行模型

Windows 将应用程序隔离在独立的用户态虚拟地址空间中，由内核统一管理进程、线程、内存、对象、安全和 I/O。处理器真正调度的是线程；进程提供地址空间、句柄表、安全上下文和资源容器。

```text
应用代码 / 运行库 / Win32 API
            ↓
        ntdll.dll
            ↓
        系统调用边界
            ↓
    内核执行体与驱动
            ↓
  对象、内存、I/O、调度器
```

这个分层是理解调用链的基础。CreateFileW、VirtualAlloc 等 Win32 API 往往还会调用 KernelBase/Kernel32 和 ntdll 中的 Native API，随后才通过系统调用进入内核。不同 Windows 版本的内部实现可能变化，因此分析时不要写死中间函数数量。

## 0x01 用户态与内核态

用户态代码只能直接访问当前进程允许访问的用户地址和资源；内核态代码具有更高权限，可以访问系统空间，并在当前进程上下文中访问相应用户空间。权限边界由处理器特权级、页表权限和操作系统检查共同实现。

- 用户态异常通常只影响当前进程，未处理异常最终导致进程终止。
- 内核态错误可能影响整个系统，未处理的严重异常可能触发 Bug Check。
- 进入内核不等于自动获得所有权限；内核组件仍会执行对象访问、令牌和参数检查。
- 用户指针进入内核后必须被谨慎验证，因为映射状态可能变化。

### 1.1 系统调用不是普通 CALL

用户态调用 Native API 后，会准备系统调用号和参数，再通过处理器提供的系统调用指令切换到内核入口。系统调用号与内部实现并不保证跨版本稳定；逆向工具应优先识别语义和导出函数，而不是永久写死编号。

```text
Win32 API
 -> KernelBase/Kernel32
 -> ntdll!Nt*/Zw*
 -> syscall
 -> 内核系统服务
 -> 返回用户态
```

## 0x02 进程：地址空间与资源容器

进程包含私有虚拟地址空间、句柄表、访问令牌、已加载模块、环境信息和至少一个线程。PID 只是系统分配的标识，不是对象本身，也不会永久唯一；进程退出后 PID 可能被复用。

- 映像：创建进程时映射的主 EXE。
- 模块：主映像和后续装载的 DLL。
- 句柄表：当前进程可使用的对象引用。
- 主令牌：描述进程默认安全身份和权限。
- PEB：用户态可见的进程环境数据。
- 线程集合：共享地址空间和多数进程资源。

### 2.1 创建进程的观察链

```text
创建请求
 -> 解析映像与启动属性
 -> 创建进程对象和地址空间
 -> 创建初始线程
 -> 映射 ntdll、主映像及依赖
 -> Loader 初始化
 -> TLS/运行库初始化
 -> 到达程序入口点
```

CreateProcess 返回成功并不代表业务入口已经执行。调试器可能在进程创建事件、系统断点、TLS 回调、运行库入口或用户入口中的任一阶段暂停。记录断点所处阶段，才能正确解释当时的模块和线程状态。

## 0x03 线程：系统真正调度的执行单元

线程拥有独立的寄存器上下文、用户栈、内核栈、TEB、调度状态和线程局部数据。同一进程中的线程共享地址空间，因此一个线程写入全局变量或堆对象，其他线程通常可以观察到。

- 就绪：可以运行，等待处理器。
- 运行：当前在处理器上执行。
- 等待：等待事件、互斥体、I/O、定时器或其他条件。
- 终止：执行结束，线程对象可能因仍有引用而暂时存在。

线程调度受优先级、时间片、等待唤醒、处理器亲和性和系统策略影响。动态分析中的执行顺序不是固定事实；竞态问题必须通过多次运行、同步对象和时间线记录验证。

### 3.1 用户栈与内核栈

线程在用户态和内核态执行时使用不同的栈。用户态调试器通常展示用户栈；进入系统调用或处理中断时，内核使用对应的内核栈。调用栈是根据返回地址、展开信息和栈内容恢复的分析结果，栈损坏时可能不完整。

## 0x04 PEB 与 TEB

PEB（Process Environment Block）保存进程级用户态信息，TEB（Thread Environment Block）保存线程级信息。它们经常出现在加载器、运行库、异常处理、反调试和手工解析模块的代码中。字段布局属于实现细节，跨架构和版本分析时应使用与目标系统匹配的符号或结构定义。

- PEB：映像基址、Loader 数据、进程参数、堆相关信息及部分全局标志。
- PEB_LDR_DATA：维护已加载模块相关链表和状态。
- RTL_USER_PROCESS_PARAMETERS：命令行、环境、当前目录及标准句柄等用户态参数。
- TEB：线程 ID、栈边界、TLS、LastError、异常和运行库线程状态。

```text
x86：常通过 FS 访问 TEB
x64：常通过 GS 访问 TEB

示例语义：
TEB -> ProcessEnvironmentBlock -> PEB
PEB -> Ldr -> 已加载模块信息
```

恶意软件或保护壳可能直接遍历 PEB 模块链表来避免导入 API。看到 GS/FS 相对访问和模块链表遍历时，应结合字符串哈希、导出表解析和最终函数调用确认目的。

## 0x05 句柄、对象和引用

Windows 对文件、进程、线程、事件、互斥体、节对象、注册表键和访问令牌等资源使用对象模型。用户态通常通过句柄访问对象；句柄是当前进程句柄表中的索引化引用，不是内核对象地址。

- 句柄值只在所属进程和指定上下文中有意义。
- 同一个内核对象可以被多个进程以不同句柄值引用。
- 复制句柄会创建新的句柄表项，并可调整继承和访问权限。
- 关闭句柄减少句柄引用；对象是否销毁还取决于其他句柄和内核引用。
- 伪句柄由 API 解释，不一定对应普通句柄表项。

```text
用户态 HANDLE
 -> 当前进程句柄表项
 -> 对象指针 + 授予的访问权限
 -> 对象头与类型相关对象体
```

### 5.1 句柄泄漏与悬空概念

忘记 CloseHandle 会导致句柄表持续增长和对象生命周期延长。句柄关闭后数值可能被重新使用，因此日志中相同的句柄值不代表始终指向同一对象。逆向时应同时记录时间、对象类型和创建来源。

## 0x06 对象命名空间

部分内核对象具有名称，并组织在对象管理器命名空间中。Win32 路径、NT 对象路径和 DOS 设备路径可能指向同一底层对象，但书写方式不同。分析路径时应区分文件系统路径与对象管理器路径。

```text
Win32：C:\Windows\System32\example.dll
NT：    \??\C:\Windows\System32\example.dll
设备：  \Device\HarddiskVolumeX\Windows\System32\example.dll
对象：  \BaseNamedObjects\ExampleEvent
```

命名事件、互斥体和共享节常用于进程间协调。单独发现一个名称只能证明程序引用了该对象，不能直接证明其用途；应继续观察创建参数、访问权限和等待/设置操作。

## 0x07 访问令牌与权限检查

访问令牌描述安全主体、组、特权、完整性级别和其他安全属性。进程通常拥有主令牌，线程可以临时使用模拟令牌。对象访问检查会结合令牌、请求权限、对象安全描述符和系统策略决定是否允许。

- SID：标识用户、组或服务身份。
- Privilege：执行特定系统级操作的能力，存在于令牌中不等于当前已启用。
- Integrity Level：参与强制完整性控制，影响低完整性进程写入高完整性对象。
- Impersonation：线程临时代表其他安全上下文访问资源。
- Access Mask：调用者请求的具体权限位。

管理员组成员不等于所有操作都自动以完整管理员令牌执行。UAC、令牌过滤、服务身份和模拟状态都会改变权限判断。动态分析权限失败时，应记录令牌状态和 GetLastError/NTSTATUS，而不是只看用户名。

## 0x08 虚拟地址空间

每个用户进程拥有独立虚拟地址空间。虚拟地址通过页表映射到物理页、文件页或尚未实际提交的状态；连续虚拟地址不要求对应连续物理内存。工作集表示当前驻留在物理内存中的部分页面。

- Private：进程私有页面，例如堆和匿名 VirtualAlloc 内存。
- Mapped：由节对象或文件映射产生。
- Image：按映像规则映射的 EXE/DLL。
- Free：尚未保留的地址范围。
- Reserved：保留地址范围，但未必有实际存储。
- Committed：已承诺可由物理内存或分页文件提供后备存储。

### 8.1 Reserve 与 Commit

```c
VirtualAlloc(NULL, size, MEM_RESERVE, PAGE_NOACCESS)
  -> 预留地址范围，不保证所有页面已有物理存储

VirtualAlloc(base, size, MEM_COMMIT, PAGE_READWRITE)
  -> 提交页面，首次访问时可能发生缺页并分配实际页面
```

Reserved、Committed 和 Resident 是不同维度。页面已经提交，不代表此刻驻留物理内存；发生缺页也不一定是错误，可能只是正常按需调页。

### 8.2 页面权限

- PAGE_READONLY：可读，不可写。
- PAGE_READWRITE：可读写。
- PAGE_EXECUTE_READ：常见代码页权限。
- PAGE_EXECUTE_READWRITE：允许写入并执行，是自修改、JIT 和解密代码的重要观察点。
- PAGE_GUARD：首次访问产生 Guard Page 异常，常用于栈增长或监控访问。
- PAGE_NOACCESS：任何访问都会触发异常。

权限变化是行为证据，但不能孤立下结论。VirtualProtect 把 RW 内存改成 RX 可能是 JIT、壳解密、运行时补丁或正常框架行为，需要结合写入内容和后续控制流判断。

## 0x09 页、缺页与写时复制

内存以页面为管理单位。访问尚未驻留但有效的页面时，处理器触发缺页，内存管理器将页面调入或完成映射；访问无效地址或违反权限时，则形成访问冲突。

映像和映射文件的只读页面可以被多个进程共享。对于写时复制页面，多个进程最初共享物理页，当某个进程写入时，系统为该进程创建私有副本。因此修改自己进程中的 DLL 数据通常不会直接修改其他进程或磁盘文件。

## 0x0A 堆、栈与映射内存

堆用于大小和生命周期动态变化的分配；栈主要承载调用链、局部状态和返回信息；文件映射适合共享文件内容或进程间共享。三者最终都建立在虚拟内存机制上，但管理者和生命周期不同。

- 进程堆：进程启动时创建，运行库和应用可继续创建额外堆。
- 低碎片堆等策略属于实现细节，不应仅根据几个堆块推断全部分配器行为。
- 线程栈：通常先保留较大范围，再按需提交，并使用 Guard Page 扩展。
- 文件映射：CreateFileMapping/MapViewOfFile 通过节对象建立视图。

堆块头、空闲链和内部元数据会随系统版本、配置和调试选项变化。分析堆损坏时，应优先使用匹配版本的调试扩展，而不是写死内部偏移。

## 0x0B DLL 加载流程

DLL 可以在进程启动时因导入关系被装载，也可以由 LoadLibrary/LoadLibraryEx 在运行时装载。加载器需要定位文件、映射映像、处理重定位、解析依赖、修复导入、完成 TLS 和初始化通知。

```text
查找 DLL
 -> 检查是否已加载及引用状态
 -> 建立映像映射
 -> 处理重定位
 -> 解析依赖和 IAT
 -> 初始化 TLS/运行时
 -> 调用入口点通知
 -> 返回模块句柄
```

- LoadLibrary 返回的 HMODULE 在用户态通常可视为模块基址。
- 重复装载已存在模块通常增加引用计数，而不是再次映射一份。
- FreeLibrary 减少引用计数，归零后模块才可能卸载。
- DllMain 在 Loader Lock 相关上下文中执行，应避免复杂装载、同步和线程等待。

### 11.1 DLL 搜索路径

DLL 搜索顺序受到调用方式、完整路径、应用目录、系统目录、SafeDllSearchMode、AddDllDirectory/SetDefaultDllDirectories、打包环境和 Side-by-Side 配置等因素影响。分析 DLL 劫持或装载异常时，必须记录目标系统和实际搜索结果，不能只背一条固定顺序。

### 11.2 Loader Lock

加载器在模块装载、卸载和初始化期间需要保护内部状态。DllMain 中执行 LoadLibrary、等待其他线程或调用可能间接获取 Loader Lock 的代码，可能造成死锁或重入问题。逆向卡死时，可检查线程栈是否停留在加载器内部并互相等待。

## 0x0C PEB 模块链表与模块枚举

常规工具可以通过公开 API 枚举模块；低层代码也可能从 PEB 的 Loader 数据结构遍历模块。标准 Loader 管理的模块通常出现在相关结构中，但手工映射模块可能绕过正常记录。

- 模块未出现在常规模块列表中，不等于它不存在；检查可执行私有内存和映像特征。
- 模块出现在列表中，也不等于其所有代码仍与磁盘一致；页面可能被补丁、Hook 或写时复制修改。
- 比较内存映像与磁盘时，应排除重定位、IAT 修复和正常运行时差异。

## 0x0D I/O 与等待模型

Windows I/O 通常围绕句柄、缓冲区、偏移、完成状态和驱动栈展开。同步 API 在操作完成前返回得较晚；异步/重叠 I/O 可以立即返回，并通过事件、完成例程或 I/O Completion Port 通知结果。

- 文件句柄不仅可以代表磁盘文件，也可能指向设备、管道或通信端点。
- ReadFile/WriteFile 的行为取决于句柄类型、打开标志和是否使用 OVERLAPPED。
- ERROR_IO_PENDING 常表示异步请求已接受但尚未完成，不等于最终失败。
- 线程等待 I/O 时通常不占用 CPU，完成后由调度器重新置为可运行。

## 0x0E 同步对象与并发

- Event：有信号/无信号状态，适合通知。
- Mutex：跨线程或跨进程互斥，并具有所有权概念。
- Semaphore：计数型资源控制。
- Critical Section：主要用于进程内同步，通常比内核互斥体轻量。
- SRWLOCK：支持共享/独占访问。
- Waitable Timer：在指定时间使等待线程继续执行。

死锁分析不能只看“线程都在等待”。应记录每个线程持有哪些锁、正在等待哪个对象，以及锁获取顺序。竞态分析则要定位共享数据、缺少同步的访问和不同线程的时间关系。

## 0x0F Windows 消息与 GUI 线程

GUI 线程通常拥有消息队列，通过 GetMessage/PeekMessage 读取消息，再由 DispatchMessage 调用窗口过程。窗口过程只是消息处理入口，实际业务可能继续调用对象方法、发送异步任务或跨线程通信。

```text
系统/应用产生消息
 -> 线程消息队列
 -> GetMessage / PeekMessage
 -> TranslateMessage
 -> DispatchMessage
 -> WindowProc
```

SendMessage 可能同步等待目标窗口过程返回，PostMessage 只投递消息。跨线程同步发送消息和锁组合不当可能形成死锁。分析按钮行为时，可从窗口过程、命令 ID 和消息分发继续追踪实际处理函数。

## 0x10 异常分发：从异常点到处理器

处理器故障、软件 RaiseException、断点和单步都可以生成异常。系统保存线程 CONTEXT 和 EXCEPTION_RECORD，然后按照调试器、VEH、帧式异常处理等机制尝试分发。具体顺序和二次机会行为应结合调试状态理解。

```text
异常发生
 -> 保存 CONTEXT / EXCEPTION_RECORD
 -> 调试器第一次机会
 -> VEH / 帧式处理器等分发
 -> 若已处理则按指定上下文继续
 -> 未处理时进入后续机会和默认终止流程
```

- ExceptionCode：异常类型，例如访问冲突、断点、除零。
- ExceptionAddress：异常发生位置。
- ExceptionInformation：某些异常附带读写类型和目标地址等参数。
- CONTEXT：异常时寄存器和执行状态。

### 16.1 SEH 与 VEH

SEH 是 Windows 的结构化异常处理体系。x86 传统帧式处理与线程异常链关系密切；x64 更依赖函数表和展开元数据。VEH 是进程范围的向量异常处理机制，可在调试、保护壳和运行时监控中出现。C++ 异常通常构建在平台异常机制之上，但二者不能简单等同。

遇到异常驱动控制流时，不要直接把异常当作崩溃。记录异常码、第一次/第二次机会、处理器返回值、修改后的 CONTEXT 以及最终 RIP/EIP，才能判断异常是正常逻辑、反调试、解密调度还是实际错误。

## 0x11 调试器与异常

- 断点异常：软件断点通常通过修改指令字节产生。
- 单步异常：Trap Flag 或硬件调试机制使处理器逐步产生事件。
- First Chance：应用处理器尚未最终拒绝该异常，调试器先获得观察机会。
- Second Chance：异常未被应用处理，继续执行通常意味着进程即将终止。

调试器“在异常处停下”不代表程序原本会崩溃。应继续观察应用是否注册处理器并恢复执行；反过来，忽略所有第一次机会异常也可能错过真正的根因。

## 0x12 Native API、NTSTATUS 与 Win32 错误

Win32 API 常用 BOOL、HANDLE 或特定返回值表示成功失败，并通过 GetLastError 提供扩展信息。Native API 常返回 NTSTATUS。两套错误体系不能直接混用，且 LastError 只有在 API 文档说明失败后有效时才应读取。

```c
Win32：
if (!SomeApi(...)) { err = GetLastError(); }

Native：
NTSTATUS status = NtSomeCall(...);
if (!NT_SUCCESS(status)) { ... }
```

逆向时应在失败分支立即记录返回值和错误码，因为后续 API 可能覆盖线程的 LastError。看到 SetLastError 或 TEB 中的 LastErrorValue 访问时，通常是在维护 Win32 错误语义。

## 0x13 WOW64 与跨架构观察

在 64 位 Windows 上运行的 32 位进程处于 WOW64 环境。它仍使用 32 位用户地址和 32 位模块，同时通过兼容层进入 64 位系统环境。文件系统和注册表访问还可能受到重定向规则影响。

- 不要用 64 位调用约定解释 32 位模块。
- 调试器、扩展和注入模块的架构必须匹配目标场景。
- 同名系统 DLL 可能存在 32 位与 64 位版本。
- 路径中 System32、SysWOW64 的实际含义容易与名称直觉相反，应观察真实打开路径。

## 0x14 服务、会话与桌面

服务通常由 Service Control Manager 管理，运行在特定服务账户和会话环境中。会话、窗口站和桌面影响 GUI 对象、输入与可见界面。服务进程能否显示窗口、访问用户资源或读取用户配置，取决于身份、会话和权限，而不只是进程名。

## 0x15 逆向分析中的系统观察点

- 进程创建：CreateProcess、NtCreateUserProcess 及启动属性。
- 模块装载：LoadLibrary/LdrLoadDll、模块基址、引用计数和 Loader 事件。
- 内存：VirtualAlloc、VirtualProtect、映射视图和可执行权限变化。
- 对象：Create/Open/Close、句柄复制、命名对象和访问掩码。
- 文件注册表：实际路径、重定向、返回状态和缓冲区内容。
- 线程同步：创建、等待、唤醒、锁顺序和线程退出。
- 异常：异常码、上下文、处理器和恢复地址。
- 安全：进程/线程令牌、完整性级别、特权和模拟状态。

## 0x16 一个可复现的综合实验

```text
实验程序执行以下动作：
1. 输出 PID/TID 和模块基址
2. VirtualAlloc 一页 RW 内存并写入标记
3. VirtualProtect 改为只读，再恢复为 RW
4. 创建命名 Event 和工作线程
5. 工作线程等待 Event，主线程设置 Event
6. LoadLibrary 加载一个自编写 DLL，再 FreeLibrary
7. 使用 __try/__except 捕获一次受控异常
```

- Process Explorer：观察进程、线程、句柄和令牌。
- VMMap：观察映像、堆、栈和私有内存区域变化。
- x64dbg/WinDbg：记录模块装载、线程切换、异常和地址。
- Process Monitor：记录文件、注册表和进程事件。
- 程序日志：保存每一步返回值、GetLastError、地址和线程 ID。

实验的目标不是制造复杂行为，而是把同一个事件在 API 返回值、调试器、系统工具和内存视图中对齐。只要四种观察结果能够互相解释，就建立了可迁移的 Windows 系统模型。

## 0x17 常见误区

- 把进程当作调度单位；实际上调度器运行线程。
- 把 HANDLE 当作对象地址；它只是当前句柄表中的引用。
- 把 Reserve、Commit 和物理驻留混为一谈。
- 看到缺页就认为程序出错；许多缺页属于正常按需调页。
- 认为 LoadLibrary 总会重新映射 DLL；已加载模块通常增加引用状态。
- 在 DllMain 中看到复杂逻辑却忽略 Loader Lock 风险。
- 认为第一次机会异常就是崩溃；应用仍可能正常处理。
- 将 GetLastError 随时读取的值当作当前 API 错误。
- 写死 PEB/TEB 或内核结构偏移，不考虑版本和架构。

## 0x19 资料与交叉验证

Windows 内部机制容易随系统版本变化。对象、虚拟内存、进程线程和异常的通用概念可与 Microsoft 文档交叉确认；PEB/TEB、Loader 和具体内核结构则应结合目标系统符号、WinDbg 输出和实际样本验证。看雪论坛中的 Windows 内核、进程线程、系统调用和 Loader 实战文章适合补充调试路径，但帖子中的固定偏移、系统调用号和结构布局只能用于其对应版本。

## 0x1A 总结

Windows 逆向的系统视角可以归纳为五条主线：线程在进程地址空间中执行；虚拟内存决定代码和数据如何存在；对象管理器和句柄连接系统资源；访问令牌决定能否操作对象；Loader、异常和系统调用连接用户代码与系统机制。分析具体行为时，把 API、对象、地址、线程和返回状态放在同一条时间线上，才能避免只看到局部代码而误判整体行为。
