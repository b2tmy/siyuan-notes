# 动态调试

# 动态调试

动态调试是在程序真实运行过程中观察并控制执行，通过断点、单步、寄存器、内存、线程、异常和调用栈验证静态假设。它最适合回答“这次运行实际经过哪里、参数是什么、数据何时改变、返回值如何影响后续路径”。

调试器显示的是特定输入、环境和时间点下的现场。一次运行没有经过某条路径，不代表该路径不可达；一次运行观察到某个地址，也不代表下次仍是同一绝对地址。所有记录应包含触发步骤、线程、模块基址和地址坐标。

## 0x00 调试前的实验设计

- 明确问题：寻找校验函数、追踪缓冲区、确认异常、定位按钮事件或观察模块装载。
- 准备基线：原始样本哈希、启动参数、工作目录、输入文件和系统环境。
- 选择入口：静态 RVA、字符串、API、异常、内存写入或用户操作。
- 定义证据：需要记录哪些寄存器、内存、线程、返回值和调用栈。
- 定义停止条件：何时说明假设成立，何时需要改变输入重新实验。

```text
问题：配置中的 token 在哪里被校验？
输入 A：token=AAAA
输入 B：token=AAAB
断点：配置读取 API、候选解析函数、比较分支
记录：缓冲区地址、长度、调用栈、返回值、最终分支
停止：能够预测第三组输入的执行结果
```

## 0x01 启动调试与附加调试

启动调试从进程创建阶段介入，适合观察入口、TLS、早期初始化和模块装载。附加调试连接已运行进程，适合分析需要手动操作、复杂启动器或长期运行服务的程序。

- 启动：控制更早，但调试环境可能改变启动时序。
- 附加：保留程序原有启动过程，但会错过早期事件。
- 子进程：目标行为可能发生在启动器创建的另一个进程中。
- 服务：需要确认实际服务进程、账户、会话和架构。
- GUI：先使程序稳定运行，再围绕用户操作建立断点。

Attach 本身会引入调试事件和线程状态变化。涉及竞态、超时或反调试时，应比较正常运行和调试运行的差异。

## 0x02 调试器首次暂停位置

首次暂停可能位于系统断点、Loader 事件、TLS 回调、模块入口或用户设置的断点。不要看到 RIP/EIP 就认为已经到主程序逻辑，应先检查当前模块、调用栈和内存映射。

```text
系统断点
 -> 模块装载事件
 -> TLS / Loader 初始化
 -> PE EntryPoint
 -> 运行库入口
 -> main / WinMain
 -> 业务事件
```

## 0x03 运行、暂停与单步

- Run：继续执行直到断点、异常或进程事件。
- Pause：请求暂停当前调试对象，暂停位置可能不在业务代码。
- Step Into：执行一条指令，CALL 时进入目标。
- Step Over：执行一条指令，CALL 通常整体完成后停在下一条。
- Run Until Return：运行到当前函数返回，依赖正常栈和返回流程。
- Run to User Code：尝试跳过系统模块，但工具对“用户模块”的判断需要确认。

单步不是默认答案。未知函数、关键比较和状态变化附近适合步入；已知库函数可步过；大循环应使用条件断点或运行到目标，而不是逐条执行。

## 0x04 软件断点

软件断点通常用断点指令临时替换目标位置的原始字节。命中后调试器恢复和管理执行，因此它适合普通代码地址，但会修改被调试进程内存，可能被完整性检查发现。

- 优点：数量通常不受少量硬件槽位限制，使用方便。
- 限制：需要目标页面可写或由调试器处理权限，且会改变代码字节。
- 风险：自校验、解密覆盖、代码重写可能使断点丢失或触发检测。
- 记录：保存断点地址时使用模块名 + RVA。

## 0x05 硬件断点

硬件断点利用处理器调试寄存器监视执行或数据访问，不需要改写目标字节。槽位数量有限，长度和对齐受到架构限制，线程上下文切换时由系统维护。

- 执行断点：在指定地址执行时停止。
- 写入断点：目标范围被写入时停止。
- 访问断点：目标范围被读取或写入时停止。
- 线程差异：确认调试器将硬件断点应用到哪些线程。

追踪“谁修改了这个字段”时，硬件写入断点通常比在大量候选代码处下断更高效。命中后应检查当前指令、写入宽度、旧值、新值和调用栈。

## 0x06 内存断点与 Guard Page

内存断点通常依赖页面保护或调试引擎机制，粒度可能是页面而不是单个变量。监视一个小字段时，同页其他访问也可能频繁触发。

- 适合监视未知代码何时访问一段缓冲区。
- 适合捕获解密后数据首次执行或首次读取。
- 高频访问页面可能产生大量噪声。
- 命中后保护状态可能需要调试器重新设置。

x64dbg 支持为内存断点设置条件，使只有表达式满足时才真正暂停。条件和地址表达式应根据当前工具版本测试，避免误认为没有命中。

## 0x07 DLL 与异常断点

- DLL 断点：模块加载或卸载时暂停，适合插件、动态依赖和延迟装载。
- 异常断点：针对指定异常码或异常类别暂停。
- 入口断点：模块到达入口点时暂停。
- API 断点：在导出函数或调用点观察参数与返回值。

模块加载事件经常发生在 Loader 内部，此时 Loader Lock 和初始化状态会影响可安全执行的操作。记录模块路径、基址和触发线程，再选择模块内 RVA 设置后续断点。

## 0x08 条件断点

条件断点把“每次命中都暂停”改为“只有条件满足才暂停或记录”。它是降低高频 API、循环和多线程噪声的核心工具。

```text
候选条件语义：
- 仅特定线程：tid() == TARGET_TID
- 参数长度：r8 == 40h
- 返回值失败：rax == 0
- 指针非空且内容匹配：检查 rcx 指向字符串
- 命中次数：只在第 N 次或范围内暂停
```

x64dbg 表达式默认数值书写规则、内存解引用和字符串函数有自己的语法。方括号通常表示读取内存；要比较字符串应使用对应字符串函数，而不是把指针直接与文本比较。

### 8.1 暂停条件、日志条件和命令

- 暂停条件：决定命中后是否中断。
- 日志条件：决定是否写入日志。
- 日志文本：格式化输出寄存器、内存和表达式结果。
- 命令条件：决定是否执行断点命令。
- 命令：可修改变量、记录数据或继续运行。

先让条件只写日志、不暂停，可以验证表达式是否正确并减少对时序的影响。确认日志符合预期后，再启用暂停条件。

## 0x09 跟踪与 Trace

Trace 会逐条执行并记录指令、寄存器或表达式。它适合缩小后的关键范围，不适合从程序启动开始无限追踪，因为日志会快速膨胀并显著改变执行时序。

- Step Into Trace：进入 CALL，信息最完整但数据量最大。
- Step Over Trace：跳过 CALL 内部，适合先看函数级路径。
- 条件跟踪：仅记录或暂停符合条件的位置。
- Trace Recording：保存执行过的地址和状态，便于回看。
- 覆盖率思路：比较不同输入触达的基本块或函数。

看雪关于 x64dbg 条件追踪的实践强调：先粗定位关键 CALL，再对小范围逐条跟踪。这样既减少系统模块和无关函数产生的日志，也能保留参数、返回值和关键跳转。

## 0x0A 寄存器观察

寄存器值必须结合当前指令和调用约定解释。Windows x64 前四个整数或指针参数通常位于 RCX、RDX、R8、R9，返回值常在 RAX；x86 参数通常更多依赖栈。

```text
调用前记录：
RIP = module + RVA
RCX = 参数1
RDX = 参数2
R8  = 参数3
R9  = 参数4
RSP = 调用前栈顶

返回后记录：
RAX / XMM0
ZF/CF/SF/OF
输出缓冲区与对象字段
```

寄存器窗口中的值只是当前时刻快照。步过一个函数后，易失寄存器可能全部改变；需要保留的参数应在调用前记录，返回值应在调用后立即记录。

## 0x0B 栈与调用栈

栈窗口展示原始内存，调用栈窗口根据返回地址和展开信息恢复函数链。两者应交叉使用：调用栈帮助定位上层业务函数，原始栈用于核对参数、返回地址和异常现场。

- 当前返回地址通常位于栈顶附近，但函数序言和调用约定会改变布局。
- Windows x64 存在 shadow space，不能把所有 [rsp+offset] 都当作普通参数。
- 调用栈缺失可能源于优化、尾调用、栈损坏或缺少展开信息。
- 可疑返回地址应检查是否落在可执行模块和 CALL 后续位置。

## 0x0C 内存窗口与数据解释

同一段内存可以按字节、整数、浮点、指针、字符串或结构体解释。选择解释方式前先确认地址有效、页面权限、数据宽度和编码。

- Dump：观察连续内存和指针跟随。
- Stack：观察当前线程栈。
- Memory Map：确认区域 Base、Size、Type 和 Protection。
- Modules：把地址归属到具体模块和 RVA。
- Symbols：使用 PDB 或导出名称提高可读性。

发现缓冲区后应记录基址、长度、创建位置、写入位置和消费位置。只保存一张十六进制截图，很难解释它何时有效以及谁拥有它。

## 0x0D 追踪数据写入

```text
目标：对象字段 [object+0x30] 何时变为 1
1. 在对象创建后确认 object 地址
2. 对 object+0x30 设置硬件写入断点
3. 触发目标操作
4. 命中时记录当前指令、旧值/新值和调用栈
5. 返回静态工具标注写入函数及条件
```

若对象地址每次运行变化，应先在构造函数、分配函数或保存对象指针的位置获得本次地址，再动态设置数据断点。

## 0x0E 从 API 断点回溯业务代码

当业务入口未知时，可以在与目标行为相关的系统 API 上断下，再通过调用栈向上找到用户模块的调用者。例如文件、注册表、网络、内存权限和窗口消息 API 都可作为观察点。

- 先设置参数条件，避免系统中大量无关调用。
- 命中后确认调用来自目标进程和目标线程。
- 沿调用栈找到第一个用户模块函数。
- 在用户调用点设置新的模块 RVA 断点。
- 移除宽泛 API 断点，转入业务函数分析。

API 断点只能证明本次路径调用了该接口。参数、返回值和调用栈比 API 名称更重要，同一 API 可以承担完全不同的业务用途。

## 0x0F 返回值断点与“步出”

想观察函数返回值时，可以在 CALL 后下一条指令设置一次性断点，或使用运行到返回功能。对于递归、异常、尾调用或被破坏的栈，简单步出可能不可靠。

```asm
call target
next_instruction:       ; 在这里观察 RAX/XMM0 和输出参数
test eax, eax
je failed
```

函数返回值常与输出参数共同构成结果。仅观察 RAX 可能漏掉缓冲区、对象字段、LastError 或 NTSTATUS 的变化。

## 0x10 模块与 ASLR

ASLR 使模块每次加载基址可能变化。静态地址和动态地址通过 RVA 对齐：RuntimeVA = RuntimeModuleBase + RVA。断点数据库如果由调试器按模块保存，通常可以在下次加载时重定位，但人工笔记仍应记录模块名和 RVA。

```text
静态工具地址：0x140012340
静态 ImageBase：0x140000000
RVA：0x12340

本次运行基址：0x00007FF700000000
运行地址：0x00007FF700012340
```

## 0x11 线程调试

多线程程序中，任何线程都可能命中共享代码或数据断点。命中后先记录 TID、线程入口、当前调用栈和其他线程状态，再判断是否为目标线程。

- 线程切换：查看每个线程的 RIP、栈和等待状态。
- 冻结线程：可减少干扰，但可能造成锁等待和时序失真。
- 线程条件：让断点只响应指定 TID。
- 竞态：多次运行并记录事件顺序，不能依赖单次观察。

暂停所有线程会改变程序时序。分析锁、消息、网络和超时时，应尽量使用日志断点或短暂停留，并比较无调试器运行结果。

## 0x12 异常调试

异常可能是实际错误，也可能是断点、单步、受控探测、反调试或正常异常处理。判断依据包括异常码、异常地址、第一次/第二次机会、处理器和恢复后的控制流。

- 第一次机会：调试器先看到，应用仍可能处理。
- 第二次机会：应用未处理，继续执行通常会终止进程。
- 访问冲突：记录读/写/执行类型和目标地址。
- Guard Page：可能是栈增长、监控访问或保护逻辑。
- 断点/单步异常：可能由调试器或程序主动触发。

```text
异常记录
Code：
Address：module+RVA
Thread：
Chance：First / Second
Access：Read / Write / Execute
Target Address：
Handler：
恢复后的 RIP：
```

## 0x13 模块加载与 Loader 事件

动态加载的 DLL、插件和运行时组件可能在目标操作发生后才出现。设置 DLL 加载断点或观察模块列表，可以确定加载时机、路径和基址。

- 记录完整路径，区分同名模块。
- 入口断点之前可能先执行 TLS 和 Loader 初始化。
- DllMain 运行在特殊加载上下文中，调用栈可能包含大量 Loader 代码。
- 模块卸载后旧地址可能失效或被其他映射复用。

## 0x14 GUI 事件定位

GUI 程序的业务逻辑常由窗口消息、命令 ID、回调或框架事件触发。可以先使用窗口工具确认控件和消息，再在窗口过程、消息分发、按钮命令或相关字符串处定位。

```text
用户点击
 -> 消息队列 / 框架事件
 -> WindowProc / 消息映射
 -> 控件回调
 -> 业务函数
 -> 状态变化或输出
```

对复杂 GUI，可在一次目标操作前后比较函数调用次数或跟踪覆盖范围。看雪的函数调用统计实践就是通过触发前后次数变化筛选关键 CALL，但筛选结果仍需人工确认参数和副作用。

## 0x15 命令行程序与输入定位

命令行程序可以从 main/入口参数、ReadFile、标准输入、文件解析或环境变量进入业务逻辑。准备最小输入并逐步改变一个字节、字段或参数，能快速找到影响分支。

## 0x16 WinDbg 的使用场景

x64dbg 适合用户态交互式逆向；WinDbg 在符号、崩溃转储、异常、线程、堆和内核调试方面更强。两者可以针对同一地址使用模块 + RVA 对齐结果。

- 用户态 Live Debug：观察进程、线程、异常和内存。
- Dump 分析：在不重新运行样本时检查崩溃现场。
- 符号：加载 Microsoft 或私有 PDB 恢复系统调用栈。
- 扩展：分析堆、句柄、锁和异常记录。
- 内核调试：观察驱动、系统线程和内核对象，需要隔离测试环境。

## 0x17 崩溃现场分析

- 确认异常码、异常地址和故障线程。
- 查看寄存器、故障指令和访问目标。
- 检查调用栈是否可信，必要时查看原始栈。
- 确认目标地址所属内存区域和权限。
- 沿数据来源寻找 NULL、悬空指针、越界或类型错误。
- 比较正常输入和崩溃输入的最早分歧。

异常发生位置不一定是根因位置。例如堆破坏可能在较早写入时发生，直到后续分配或释放才检测出来。此时应从损坏对象向前追踪写入。

## 0x18 补丁与假设验证

临时修改寄存器、内存或跳转可以用于验证因果关系，但补丁成功并不自动等于理解正确。补丁可能绕过一个检查，却破坏后续状态。

- 修改前记录原值和地址。
- 一次只改变一个条件。
- 观察补丁后完整后续路径，而不只看当前分支。
- 重新启动恢复干净状态后重复实验。
- 永久补丁使用文件副本，并记录 FOA、原字节和新字节。

## 0x19 自动化脚本

当实验需要重复设置断点、输入参数、收集寄存器或导出内存时，可以使用调试器脚本。脚本应以稳定的模块 RVA 为基础，检查模块是否加载，并把每次运行输出到独立日志。

```text
自动化流程
1. 等待目标模块加载
2. 计算 ModuleBase + RVA
3. 设置条件断点和日志表达式
4. 运行到目标事件
5. 导出参数、返回值和内存
6. 按实验编号保存结果
```

```text
实验编号：
样本 SHA-256：
启动/附加方式：
命令行与输入：
模块基址：
断点：模块+RVA、类型、条件
命中线程：
调用前参数：
返回值与输出参数：
内存变化：
调用栈：

```

日志要能够让未来的自己在没有截图上下文时复现实验。每个十六进制地址都应说明它是 VA、RVA 还是文件偏移。

## 0x1B 常见错误

- 从系统断点开始无限单步。
- 在高频 API 上无条件暂停，导致无法到达业务操作。
- 把步过理解为“不会执行函数”；函数仍会完整执行。
- 只看寄存器，不看调用约定和内存副作用。
- 只记录一次运行的绝对地址。
- 冻结线程后忽略由此产生的死锁和超时。
- 把第一次机会异常直接当作崩溃。
- 修改寄存器或代码后继续把现场当作原始行为。
- 追踪范围过大，生成无法阅读的日志。
- 命中断点后不记录触发输入和线程。

## 0x1C 综合实验：定位一个配置校验

```text
1. 使用静态分析找到 "invalid config" 字符串和调用者 RVA。
2. 在调用者设置软件断点，使用无效配置触发。
3. 从失败输出向前观察条件跳转和返回值。
4. 在候选校验 CALL 前记录参数，在 CALL 后记录 RAX。
5. 对输入缓冲区设置读取或访问观察，确认消费位置。
6. 改变一个字段，比较路径和返回值差异。
7. 将已确认函数、参数和结构偏移回填静态数据库。
```

## 0x1D 资料与交叉验证

x64dbg 官方文档可用于确认软件、硬件、内存、DLL 和异常断点，以及条件断点、条件跟踪、线程和表达式规则。看雪论坛中的 x64dbg 入门、插件和条件追踪文章适合学习实际工作流，例如从字符串或 API 粗定位，再通过参数、返回值和条件日志筛选关键 CALL。

帖子中的快捷键、插件和表达式可能对应特定版本，使用前应在本机工具中验证。动态结论还应与静态反汇编、模块 RVA 和可重复输入交叉确认。

## 0x1E 总结

动态调试的核心不是不停按 F7/F8，而是围绕问题布置观察点。软件断点定位代码，硬件和内存断点定位数据变化，条件断点过滤噪声，调用栈连接系统 API 与业务逻辑，线程和异常解释运行时环境。每次实验只改变一个因素，并把参数、地址、返回值和最终状态记录完整，才能把一次现场观察变成可复用的结论。
