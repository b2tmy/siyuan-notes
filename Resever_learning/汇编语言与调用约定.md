# 汇编语言与调用约定

# 汇编语言与调用约定

汇编语言是逆向分析中连接机器码、寄存器、内存和高级语言语义的中间层。学习汇编的目标不是背诵每条指令，而是能够从一段指令中恢复数据流、控制流、函数边界、参数位置、返回值和副作用。调用约定则规定函数如何传参、返回、保存寄存器以及维护栈，是阅读函数调用和识别函数原型的基础。

## 0x00 阅读汇编前先固定三个坐标系

- 架构：确认是 x86、x64、ARM64 还是其他架构；同名指令在不同架构中的语义和寄存器集合不同。
- 语法：区分 Intel 语法和 AT&T 语法；前者通常是 destination, source，后者通常是 source, destination。
- 地址：记录模块名 + RVA，同时注明调试器中的运行时 VA；不要把一次运行的绝对地址当成永久地址。

```text
静态地址：module.exe + 0x1234
运行基址：0x00007FF700000000
运行地址：0x00007FF700001234

VA = ModuleBase + RVA
```

很多“看不懂汇编”的根源不是指令太难，而是地址、操作数宽度、符号性和调用约定没有先确认。每次分析函数，都先写出架构、入口地址、参数来源和返回值位置。

## 0x01 寄存器、宽度与标志位

x86/x64 通用寄存器可以保存整数、指针、参数和临时结果。x64 中 RAX、RBX、RCX 等是 64 位寄存器；访问 EAX 会使用低 32 位，并把结果写入后将 RAX 高 32 位清零；访问 AX、AL 则只影响更低的子部分。

```asm
mov rax, 0x1122334455667788
mov eax, 0xAABBCCDD   ; RAX = 0x00000000AABBCCDD
mov ax, 0x1234       ; 只修改低 16 位
mov al, 0x7F         ; 只修改低 8 位
```

- RAX/EAX：常见返回值和算术临时值。
- RCX、RDX、R8、R9：Windows x64 前四个整数或指针参数。
- RSP：栈顶，决定当前栈布局和对齐。
- RBP：可能是栈帧基址，也可能被编译器当作普通寄存器。
- RIP：指令位置；相对寻址、异常和返回地址分析都依赖它。
- RFLAGS：保存比较、算术和控制状态，条件跳转通常读取其中的 ZF、CF、SF、OF。

### 1.1 条件跳转不是“真假”两个字

CMP 本质上执行一次减法并更新标志位，Jcc 再根据标志位解释结果。JE/JZ 检查 ZF；JB/JC 使用无符号比较语义；JL 使用有符号比较语义。同一组数据接不同条件跳转，得到的业务含义可能完全不同。

```asm
cmp eax, ebx
je  equal_path       ; ZF = 1
jb unsigned_below   ; CF = 1
ja unsigned_above   ; CF = 0 且 ZF = 0
jl signed_less      ; SF != OF
jg signed_greater   ; ZF = 0 且 SF = OF
```

## 0x02 常用数据传送与算术指令

逆向时先把指令翻译成“状态变化”，再翻译成高级语言。MOV 是赋值，LEA 是地址计算而不是内存读取，TEST 常用于按位检查或判断零值，XOR 既能进行位运算也常被用于清零寄存器。

```asm
mov rax, [rcx+20h]   ; 读取 rcx+0x20 指向的内存
lea rax, [rcx+20h]   ; 计算地址 rcx+0x20，不读取内存
test eax, eax         ; 更新标志位，常用于判断 eax 是否为 0
xor eax, eax         ; eax 清零，也会更新标志位
```

- ADD/SUB：算术加减，可能影响 CF、OF、ZF、SF。
- INC/DEC：增减 1；在某些语境下对 CF 的影响与 ADD/SUB 不同。
- IMUL：有符号乘法，常用于索引、哈希和结构计算。
- SHL/SHR/SAR：左移、逻辑右移、有符号右移，常用于位域和缩放。
- AND/OR/XOR：位掩码、标志清除、异或变换和简单混淆中频繁出现。
- CMOVcc/SETcc：将条件结果变成数据，可能让控制流图看起来没有明显分支。

## 0x03 内存寻址：先判断“值”还是“地址”

Intel 语法中方括号表示访问内存。没有方括号时通常是寄存器或立即数本身，有方括号时才是从计算出的地址取值。双重方括号表示连续解引用，常见于对象指针、虚表和指针数组。

```asm
mov rax, rcx        ; rax = 指针数值
mov rax, [rcx]       ; rax = rcx 指向的内容
mov rax, [rcx+8]     ; rax = 对象偏移 8 的字段
mov rax, [[rcx]]     ; 伪写法，实际需拆成两次读取
```

结构体恢复通常从重复出现的偏移开始：同一对象指针多次使用 [reg+0x10]、[reg+0x18]，说明这些偏移可能对应稳定字段。字段类型仍需结合读写宽度、调用参数和生命周期确认。

## 0x04 栈和函数边界

CALL 通常把返回地址压入栈并跳转到目标位置，RET 从栈中取回返回地址。函数序言可能保存非易失寄存器、分配局部变量空间、建立栈帧和设置安全 cookie；函数尾声负责恢复这些状态。优化编译后，序言和尾声可能被省略或拆散。

```asm
push rbp
mov rbp, rsp
sub rsp, 40h       ; 分配局部变量空间
...
add rsp, 40h
pop rbp
ret
```

- 返回地址：定位调用者和函数返回位置。
- 局部变量：通常通过 [rsp+offset] 或 [rbp-offset] 访问。
- 保存寄存器：帮助判断哪些寄存器跨 CALL 保持不变。
- 栈平衡：调用前后的 RSP 差异必须与调用约定和清理方式一致。
- 栈对齐：调用某些 ABI 函数前必须满足规定对齐，否则可能造成崩溃或异常。

## 0x05 Windows x64 调用约定

Windows x64 常见调用约定使用 RCX、RDX、R8、R9 传递前四个整数或指针参数，浮点参数使用相应的 XMM 寄存器；第五个及之后的参数放在栈上。调用方还需要为前四个参数预留 32 字节 shadow space，即使被调函数没有使用这些位置。

```text
参数 1 -> RCX / XMM0
参数 2 -> RDX / XMM1
参数 3 -> R8  / XMM2
参数 4 -> R9  / XMM3
参数 5+ -> 栈

call 前：调用方预留 0x20 字节 shadow space
```

- 易失寄存器：RAX、RCX、RDX、R8、R9、R10、R11 以及部分 XMM 寄存器，跨调用不能假定保持不变。
- 非易失寄存器：RBX、RBP、RDI、RSI、RSP、R12-R15 等，函数若使用通常需要保存并恢复。
- 整数返回值：通常在 RAX；较大结构体可能通过隐藏返回缓冲区传递。
- 浮点返回值：通常在 XMM0。
- this 指针：在成员函数中通常作为第一个参数传入，具体表现取决于编译器和函数类型。

### 5.1 从调用点反推函数原型

```asm
lea rdx, [rsp+30h]   ; 参数 2：输出缓冲区
mov rcx, rbx          ; 参数 1：对象或上下文
mov r8d, 40h          ; 参数 3：长度
call target
test eax, eax
je failed
```

这段代码至少可以提出一个候选原型：target(context, buffer, 0x40)，返回值可能是状态码或布尔值。真正确认需要继续观察 target 内部如何读取参数、返回什么，以及调用者如何处理不同返回值。

## 0x06 x86 常见调用约定

x86 平台历史上存在多种调用约定，主要区别在参数入栈顺序、栈由谁清理、名称修饰和 this 指针位置。逆向时不能只看函数名或 ret 指令，要结合调用点和栈恢复行为判断。

- cdecl：参数通常从右到左入栈，调用者清理栈，常见于 C 函数和可变参数函数。
- stdcall：参数通常从右到左入栈，被调函数清理栈，常见于部分 Windows API。
- fastcall：部分参数通过寄存器传递，其余参数入栈；不同编译器实现可能有差异。
- thiscall：C++ 成员函数约定，this 指针通常通过 ECX 传递，其他参数按编译器规则处理。
- vectorcall：更偏向 SIMD/向量参数，不能仅凭普通整数参数模式判断。

```asm
push 3
push 2
push 1
call target
add esp, 0Ch       ; 调用者清理，符合 cdecl 形态

call target       ; 若函数尾部 ret 0Ch，可能由被调函数清理
```

x86 中 ret N 能提供线索，但优化、尾调用、异常路径和手写汇编都可能让模式不典型。最可靠的判断仍是比较多个调用点，并确认参数数量、清理方和返回值使用方式。

## 0x07 System V AMD64 与 Windows x64 的差异

Linux 和多数 Unix-like 平台常见 System V AMD64 ABI，Windows 使用 Microsoft x64 calling convention。两者都使用寄存器传参，但寄存器顺序、栈规则、shadow space 和 red zone 不同。分析跨平台样本时，必须先确定目标 ABI。

```text
Windows x64 整数参数：RCX, RDX, R8, R9
System V AMD64 整数参数：RDI, RSI, RDX, RCX, R8, R9

Windows：调用方预留 32 字节 shadow space
System V：常见 128 字节 red zone，但 Windows x64 不使用该规则
```

同一段函数如果被错误地按另一种 ABI 解读，会出现“参数数量不对”“对象指针错位”“返回值解释错误”等连锁问题。看雪的 x86-64 调用过程实战文章也强调了寄存器、栈帧和调用者/被调用者保存关系的联动分析。

## 0x08 浮点、结构体和隐藏参数

函数参数不一定都是整数。浮点值可能进入 XMM0-XMM3 或其他 XMM 寄存器；结构体可能拆分到寄存器，也可能通过隐藏的返回缓冲区指针传递。逆向 C++ 函数时，this、返回缓冲区和异常处理参数常让表面参数数量与源代码不一致。

- 先看操作数类型：标量浮点通常出现 MOVSS/MOVSD、ADDSS/ADDSD 等指令。
- 再看寄存器类别：XMM 中的值不应直接当作整数参数。
- 观察调用前是否把一块可写内存地址放入 RCX/RDI 等位置，这可能是隐藏返回缓冲区。
- 结构体字段访问和复制长度可以辅助估计结构大小，但要警惕编译器填充和对齐。

## 0x09 控制流：条件、循环和尾调用

识别控制流时，先找基本块边界，再整理条件跳转和回边。循环通常表现为计数器更新、比较和向前或向后跳转；switch 可能使用跳转表；尾调用则可能用 JMP 替代 CALL/RET。

```asm
loop_start:
  cmp ecx, edx
  jae loop_end
  mov eax, [rdi+rcx*4]
  add ecx, 1
  jmp loop_start
loop_end:
```

- CMP/TEST 后的 Jcc：条件分支。
- JMP 到更低地址：常见循环回边，但也可能是状态机或异常恢复。
- 间接 JMP [table+index*8]：可能是 switch 或虚函数分派。
- CALL 后直接 JMP：可能是尾调用、跳板或导入 thunk。
- 没有显式分支但大量 CMOV/SETcc：可能是无分支实现或编译器优化。

## 0x0A C/C++ 结构在汇编中的典型形态

- if/else：比较 + 条件跳转，或条件移动。
- for/while：初始化、条件判断、循环体、增量和回边。
- switch：范围检查后进入跳转表，或使用比较链。
- 数组：base + index * element_size。
- 结构体：base + constant_offset；嵌套结构常出现多次解引用。
- 虚函数：对象首字段常指向 vtable，再按槽位取函数地址。
- 异常：Windows x64 常伴随 unwind 信息，x86 C++ 异常可能结合 SEH 链和运行库。

```asm
mov rax, [rcx]        ; 取对象的 vtable
call qword ptr [rax+20h] ; 调用第 5 个槽位附近的虚函数
```

## 0x0B 编译优化对逆向阅读的影响

优化会改变“源码结构”和“汇编结构”的一一对应关系。函数可能被内联，变量可能只存在于寄存器，多个源码语句可能合并为一条指令，循环可能展开，尾调用可能消除返回路径。

- O0：栈变量多、结构直观，但与真实发布版本差异明显。
- O2/O3：寄存器复用、内联、循环优化和分支重排更常见。
- LTO：跨文件优化可能使函数边界、调用关系和符号更加不直观。
- 栈保护/CFG/异常展开：会插入运行库调用和额外控制流，不要误当业务逻辑。

面对优化代码，优先追踪稳定的数据和外部可观察结果，而不是强行恢复原始源码行号。对同一功能比较 Debug/Release 构建，通常比单独阅读复杂发布版本更容易建立模型。

## 0x0C 调试器中的调用验证流程

```text
1. 在调用点断下，记录模块名、RVA、RSP、参数寄存器和 XMM 寄存器。
2. 单步进入目标函数，确认函数入口是否符合预期。
3. 观察序言如何保存寄存器、分配栈空间和访问参数。
4. 在返回前记录 RAX/XMM0、内存副作用和异常状态。
5. 返回调用者，确认调用者如何解释返回值。
```

看雪实战文章中常见的做法是从调用点读取 RCX、RDX、R8、R9 等参数，再结合内存 dump 和返回前寄存器状态确认函数语义。这种“寄存器—内存—返回值”三点互证，比只看伪代码更可靠。

## 0x0D 常见错误

- 把 LEA 当成读取内存；修正：先判断是否有方括号。
- 只看 RAX 就断言返回值；修正：确认 ABI、返回类型和调用者后续使用。
- 把所有 [rsp+offset] 当作参数；修正：先画出函数序言和 shadow space/栈帧。
- 用 Windows 规则解释 Linux x64；修正：先确定平台和编译器 ABI。
- 按函数名猜参数；修正：从调用点、访问宽度和副作用反推。
- 把一次运行的 VA 写进长期笔记；修正：记录模块名 + RVA，并注明当次基址。
- 只单步不做实验；修正：改变输入，观察同一指令和返回值是否稳定响应。

## 0x0E 一个可复现的调用约定实验

```c
typedef struct { int id; const char *name; } Item;

__declspec(noinline) int calc(Item *item, int add) {
    if (!item) return -1;
    return item->id + add;
}
```

- 编译 x64 版本，在调用 calc 前观察 RCX、EDX 和 RSP。
- 进入函数后确认 RCX 被当作 Item*，[RCX] 被读取为 id。
- 改变 item->id 和 add，分别验证 RAX 返回值。
- 编译 x86 版本，再观察 this/参数入栈和返回值差异。
- 在笔记中同时记录源码、汇编、输入、寄存器和结论。

## 0x10 资料与交叉验证

看雪社区中关于 x86-64 调用过程、x64dbg 追踪和实际函数参数观察的文章，适合作为调试视角的补充材料。例如，x64dbg 实战会直接从 RCX、RDX、R8、R9 观察 Windows x64 参数，再结合返回前的 RAX 和内存内容确认函数语义；Linux x86-64 文章则展示了另一套 ABI 下的栈帧和寄存器规则。阅读论坛文章时，应将样本特例与 ABI 通用规则分开记录。

## 0x11 总结

汇编阅读可以归纳为四个动作：识别操作数、跟踪状态变化、恢复控制流、验证调用约定。寄存器不是孤立变量，栈也不是单纯的临时存储；它们共同构成函数接口和运行时状态。只要能够稳定回答“参数从哪里来、值在哪里变、结果如何返回、调用者如何解释”，就已经从背指令进入了真正的逆向分析。
