# 脱壳与壳分析

脱壳不是把文件“跑起来”或让工具自动生成一个可执行文件，而是识别保护层如何接管加载过程，观察原始代码和数据何时恢复，并把运行时映像整理成可重复分析的对象。真正需要恢复的通常不止入口点，还包括导入、节属性、重定位、TLS、异常信息以及壳在运行时修补的状态。

壳分析应围绕证据推进：磁盘文件提供静态线索，调试现场说明解压、解密和跳转过程，转储文件验证结构是否完整，重新启动后的行为验证修复是否有效。不要把“检测到某种壳”“跳到疑似 OEP”或“Dump 成功”直接当成最终结论。

## 0x00 分析边界与样本基线

- 只在隔离环境中处理来源明确的实验样本，先记录 SHA-256、文件大小、架构、签名、编译时间字段和首次获取位置。
- 保留原始样本只读副本；所有改名、补丁、转储和 IAT 修复都在副本上进行，并为每一步生成新的哈希。
- 记录操作系统版本、调试器版本、插件版本、是否联网、ASLR 状态和启动参数，保证后续能够复现。
- 分析前明确目标：确认壳类型、找到原始入口、恢复可分析映像、重建导入，还是仅解释保护机制。

```text
样本：
SHA-256：
架构：x86 / x64
文件大小：
入口点 RVA：
节表：
导入数量：
运行环境：
本轮目标：
初始假设：
```

## 0x01 壳是什么

壳位于原始程序与系统加载流程之间。系统先把带壳 PE 映射到内存并进入壳入口，壳代码再完成解压或解密、内存分配、导入解析、重定位、保护检查和控制权转移。原始程序可能仍在原节中被覆盖恢复，也可能被释放到新的私有内存区域。

```text
系统加载 PE
  -> 壳入口 Stub
  -> 环境/完整性检查
  -> 分配或选择目标内存
  -> 解压、解密、修补
  -> 解析 API 与重建运行状态
  -> 跳转或调用原始入口 OEP
  -> 原程序继续执行
```

## 0x02 壳的分类

- 压缩壳：重点是减小磁盘体积，运行时恢复代码和数据，常见实验对象包括 UPX。
- 加密壳：将关键节或资源加密，运行时按块解密，可能在使用后再次擦除。
- 保护壳：加入完整性校验、反调试、异常控制流、API 隐藏和自修改等机制。
- 虚拟化保护：把部分原生指令转换成私有字节码，由解释器或 JIT 风格调度器执行。
- 安装器与自解压包：外观与壳相似，但目标常是释放多个文件并启动安装流程，应与单映像保护区分。
- 多层壳：压缩层、保护层和业务自校验可能依次叠加，脱去一层后仍需重新建立基线。

分类的意义在于选择观察点，而不是追求标签。压缩壳可重点跟踪大块写入和最终跳转；加密壳要关注密钥、循环和页面权限；虚拟化保护则更适合先确定虚拟机边界、调度器和上下文结构。

## 0x03 静态识别：只提出候选

- 入口点位于非常规节、末节或体积很小的执行节。
- 节名异常、节权限同时可写可执行、RawSize 与 VirtualSize 差异明显。
- 高熵区域较多，但资源、压缩数据、音视频和加密配置也会产生高熵，不能单独定性。
- 导入表极小，只保留 LoadLibrary、GetProcAddress、VirtualAlloc、VirtualProtect 等加载相关 API。
- 字符串稀少、正常编译器启动代码缺失，入口附近出现解码循环、间接跳转或保存全部寄存器。
- PE 工具给出壳签名，但签名可能被修改、误撞或仅识别出编译器/安装器。

最可靠的做法是保存“支持证据”和“反证”。例如高熵加上入口解码循环和运行时大块写入可以共同支持加壳判断；若导入完整、入口直接进入 CRT、节权限正常，则应降低该判断的置信度。

## 0x04 先区分磁盘布局与内存布局

磁盘中的节使用 PointerToRawData 和 SizeOfRawData 定位，内存中的节使用 ImageBase、VirtualAddress 和 VirtualSize 定位。壳恢复的内容通常存在于内存视图，直接把内存字节覆盖到磁盘偏移会导致错位。任何转储或补丁前都应明确当前地址是 VA、RVA 还是 FOA。

```text
RVA = VA - ImageBase
FOA 需要根据所属节换算：
FOA = RVA - Section.VirtualAddress + Section.PointerToRawData

注意：仅当 RVA 落在对应节的有效范围内时才使用该式。
```

## 0x05 壳入口 Stub 的典型阶段

- 保存寄存器、标志或建立自有栈帧。
- 计算当前位置，适配 ASLR 或取得壳数据地址。
- 执行反调试、时间检查、异常探测或完整性校验。
- 定位压缩/加密数据并恢复到原节或新区域。
- 解析模块与 API，填写自建表或真正的 IAT。
- 恢复节权限、异常状态、TLS 或其他运行时结构。
- 通过直接跳转、push/ret、异常转移或间接分发把控制权交给原程序。

不同阶段可能交错执行。看到 VirtualProtect 后不能立即断言 OEP 即将出现，因为壳可能反复切换页面权限；看到大循环结束也不能立即 Dump，因为导入和重定位可能尚未恢复。

## 0x06 动态观察的关键事件

- VirtualAlloc、VirtualAllocEx、NtAllocateVirtualMemory：观察新区域的基址、大小和权限。
- VirtualProtect、NtProtectVirtualMemory：记录页面从 RW 到 RX 或 RWX 到 RX 的变化。
- WriteProcessMemory、NtWriteVirtualMemory：区分自解包与远程进程写入。
- LoadLibrary、LdrLoadDll、GetProcAddress、LdrGetProcedureAddress：确认动态导入恢复。
- CreateProcess、MapViewOfFile、NtMapViewOfSection：判断是否转入子进程、映射副本或第二阶段。
- 异常分发与 TLS 回调：确认入口点之前是否存在真实执行路径。

API 断点只是一组观测点。壳可以直接调用系统调用、手工解析 PEB 或使用哈希解析 API，因此还要结合内存写入、页面权限和控制流变化。

## 0x07 建立内存区域时间线

```text
时间 | 线程 | 事件 | 地址范围 | 旧权限->新权限 | 写入者 | 后续执行
T0   | 主线程 | 映射样本 | ImageBase.. | 文件映射 | Loader | 壳入口
T1   | 主线程 | 分配区域 | Base..Size | -- -> RW | Stub | 未执行
T2   | 主线程 | 写入完成 | Base..Size | RW | 解码循环 | 未执行
T3   | 主线程 | 改权限   | Base..Size | RW -> RX | Stub | 即将执行
T4   | 主线程 | 控制转移 | Base+RVA | RX | -- | 候选 OEP
```

时间线比单个断点更重要。候选 OEP 应与“区域由谁写入、何时变为可执行、第一次从何处进入、之后是否呈现正常程序结构”一起判断。

## 0x08 OEP 的概念与判断标准

OEP 通常指原始程序在未加壳状态下的入口点，但实际样本可能先进入 CRT、TLS、语言运行库、异常初始化或二级加载器。因此 OEP 是分析模型中的边界：从保护层恢复流程转入原程序正常初始化流程的位置。

- 控制流离开壳代码区域并进入已恢复的原映像代码。
- 附近代码符合目标架构和编译器启动模式，而不是解码循环或分发器。
- 代码区域在此前已经完成主要写入，后续不会立即被再次覆盖。
- 调用关系开始呈现 CRT、WinMain/main、DllMain 或业务初始化结构。
- 在候选点转储并修复后，文件能够独立启动且关键路径与原样本一致。

## 0x09 OEP 定位方法

- 尾部跳转法：跟踪解码循环结束后的跨区域控制转移，适合结构简单的压缩壳。
- 内存执行断点：对新写入或恢复后的区域设置执行断点，捕获第一次进入。
- 写入后执行：先定位被大规模写入的代码页，再观察其权限变化和首次执行地址。
- 模块/API 时间线：在导入恢复基本结束后，关注从壳区返回原映像的跳转。
- 栈平衡观察：比较壳入口保存的栈状态与后续恢复位置，用作候选线索。
- 已知编译器入口匹配：将候选代码与自编译样本中的 CRT/TLS 启动模式交叉验证。

## 0x0A ESP 定律及其局限

传统 x86 壳常在入口使用 pushad/pushfd 保存现场，结束时通过 popad/popfd 恢复。分析者可以在入口记录 ESP，并对保存现场所在栈地址设置硬件访问断点；当壳恢复这些值时，往往接近最终控制转移。这种方法通常被称为 ESP 定律。

- 它是经验性定位方法，不是处理器或 PE 规范中的保证。
- x64 没有 pushad/popad，编译器和壳也可能使用自定义保存区、换栈或异常恢复。
- 多线程、SEH、反调试和嵌套壳会多次访问原栈，命中不等于到达 OEP。
- 命中后仍需观察后续跳转、代码区域和程序初始化结构。

## 0x0B 内存断点与硬件断点

软件断点会修改目标字节，可能触发完整性校验；硬件断点数量有限，并受线程调试寄存器影响；内存断点通常通过页面保护异常实现，可能产生大量噪声。选择断点类型时要记录它是否改变样本可见状态。

- 入口附近的临时软件断点适合快速跟踪普通样本。
- 对少量关键地址使用硬件执行/写入断点，避免修改代码字节。
- 对较大区域使用内存访问或执行断点，并通过模块范围、线程和调用栈过滤。
- 发现断点行为异常时，使用第二种观测方式复核，例如日志、单步、快照差分。

## 0x0C 自修改代码与页面权限

自修改代码的关键证据是“同一地址的字节随时间变化”。应在写入前后保存内存快照，记录写入指令、线程、来源缓冲区和页面权限，并确认 CPU 最终执行的是哪个版本。

```text
观察流程：
1. 标记可疑 RX/RWX 区域
2. 对区域设置写入监控
3. 命中后保存修改前后字节
4. 记录写入者 EIP/RIP 与调用栈
5. 等待该区域第一次执行
6. 将执行版本送入反汇编并重新建函数
```

## 0x0D Dump 的时机

最佳转储点不是固定的某条指令，而是原映像已基本稳定的状态：主要代码和数据已经恢复，导入解析完成或可重建，关键页面权限已设置，控制流已进入原程序且壳不再覆盖目标区域。

- 过早 Dump：代码仍加密、IAT 未填、重定位和 TLS 状态未完成。
- 过晚 Dump：业务状态已改变、一次性数据被擦除、反调试或自毁逻辑已经执行。
- 多阶段样本：分别在阶段边界保存快照，比较哪一份最适合作为可分析映像。

## 0x0E 转储后需要修复什么

- AddressOfEntryPoint：改为确认后的候选 OEP RVA。
- 节的 RawSize、VirtualSize、PointerToRawData 和 Characteristics：与实际转储布局一致。
- 导入表及 IAT：恢复 DLL、函数名/序号、Thunk 数组和数据目录。
- 重定位：如果转储基址与首选基址不同，需评估是否保留或重建重定位。
- TLS：检查回调数组、索引和初始化数据是否仍然有效。
- 异常与展开信息：x64 的 pdata/xdata、C++ 异常与运行库结构不能随意丢弃。
- 资源、延迟导入、Load Config、CFG 等目录：按样本实际依赖逐项验证。

“修复 PE 头后能被工具打开”只是结构验证；“能启动一次”只是初步行为验证。还应测试不同基址、不同输入、异常路径、关键功能和重复启动。

## 0x0F IAT 与动态导入恢复

IAT 重建的目标是把运行时已解析的 API 指针重新组织成加载器能够理解的导入描述符和 Thunk。壳可能使用正常 IAT、自建指针表、API 哈希、延迟解析或在每次调用前临时解析，因此第一步是判断样本实际采用哪一种方式。

```text
IAT 重建检查：
1. 枚举候选指针区
2. 判断指针是否落入已加载模块导出范围
3. 反查 DLL 与函数名/序号
4. 合并连续 Thunk，排除普通函数指针和 vtable
5. 生成 Import Descriptor / INT / IAT / 字符串
6. 更新 Import Directory
7. 重新加载并验证每个调用点
```

- 转发导出可能最终指向另一模块，记录逻辑导入名与实际落点。
- 按序号导入不能强行转换为名称，名称在不同系统版本上可能不存在。
- GetProcAddress 返回的地址也可能只是缓存或临时变量，不能把所有 API 指针都并入 IAT。
- API Set 名称与宿主 DLL 的关系随系统版本变化，验证时保留原环境信息。

## 0x10 重定位、ASLR 与首选基址

如果壳在非首选基址恢复原映像，内存中某些绝对地址已经应用过重定位。直接把这些字节写回并把 ImageBase 改成当前基址，可能暂时可运行，却失去 ASLR 或在其他环境失败。应明确当前转储是“已重定位映像”还是“可重新重定位映像”。

- 保留原 ImageBase 时，需要恢复可用的 Base Relocation Table。
- 固定为当前基址时，应评估地址冲突和 DYNAMIC_BASE 标志，不能仅修改一个字段。
- x64 RIP-relative 指令通常不依赖基址，但数据中的绝对指针、跳转表和运行库结构仍可能依赖重定位。

## 0x11 TLS、异常和入口前执行

TLS 回调可以在 AddressOfEntryPoint 之前执行，壳也可能利用 TLS 完成解密、反调试或二阶段初始化。若只在 OEP 下断点，可能错过真正的恢复过程。

- 检查 TLS Directory、AddressOfCallbacks 和回调指针所属区域。
- 记录每个回调的调用顺序、线程和内存变化。
- x64 样本同时检查异常目录和展开信息，避免转储后异常路径崩溃。
- 若壳用异常驱动控制流，记录异常码、处理器链和继续执行地址。

## 0x12 UPX 作为基础实验样本

UPX 适合学习“壳入口—解压循环—导入恢复—跳转 OEP—转储验证”的完整闭环。实验时应优先使用自己编译的无敏感功能小程序，保留未加壳版本作为真值。

```text
建议实验：
1. 编译一个包含字符串、文件读写、TLS/异常可选项的小程序
2. 保存原文件哈希与 PE 结构
3. 使用 UPX 生成实验副本
4. 比较节、入口、导入、熵与文件大小
5. 动态记录解压区域和最终跳转
6. 在候选 OEP 转储并重建导入
7. 与未加壳版本比较代码、结构和行为
```

已知壳的官方解压功能可作为对照结果，但手工实验的价值在于理解运行时映像如何恢复。不同 UPX 版本、选项和人工修改会改变具体指令，不能死记固定地址或字节序列。

## 0x13 通用手工脱壳流程

```text
1. 建立样本基线并判断是否存在保护层
2. 描述入口 Stub 和内存区域
3. 记录分配、写入、改权限、导入解析事件
4. 捕获从壳区进入恢复区的候选边界
5. 验证候选 OEP 与编译器/运行库启动结构
6. 在稳定时机 Dump 内存映像
7. 修复节、入口、导入、重定位、TLS 和异常信息
8. 重新加载进行静态分析
9. 独立启动并执行功能回归
10. 保存证据、脚本、哈希和失败记录
```

## 0x14 多层壳与阶段化处理

多层保护不应一次性追到底。每当控制流进入新的稳定层，就保存进程快照、内存映射、模块列表、入口候选和转储文件，然后重新做一次静态基线。这样可以判断当前看到的是外层加载器、内层壳、虚拟机还是原始程序。

- 每层使用独立命名：stage0_disk、stage1_unpack、stage2_runtime。
- 记录层与层之间新增/消失的节、模块、线程、权限和导入。
- 先保证当前层可复现，再继续下一层，避免一次调试丢失全部现场。

## 0x15 虚拟化壳的分析边界

虚拟化保护通常包含入口桥接、虚拟机上下文、字节码流、调度器和多个 Handler。传统“找到 OEP 后 Dump”只能恢复未虚拟化部分；被转换成字节码的函数不会自动还原为原始机器码。

- 先识别 VM 入口和退出，确定哪些函数真正被虚拟化。
- 区分 Dispatcher、Handler、虚拟寄存器、虚拟栈和字节码指针。
- 通过多次执行比较稳定字段与变化字段，逐步建立上下文结构。
- 用输入—字节码轨迹—状态变化描述语义，避免一开始就追求完整反编译。
- 将保护层分析与业务逻辑分析分开，优先回答当前问题所需的最小语义。

## 0x16 API 哈希与手工解析

壳可能遍历 PEB 中的模块链表，再解析导出表并对函数名计算哈希，以隐藏导入字符串。分析时应定位“模块选择、名称读取、哈希计算、比较、地址返回”五个步骤，并用已知导出表验证候选算法。

```text
验证记录：
模块基址：
导出名称：
名称字节序列：
初始值：
逐字节运算：ROR/ROL/XOR/ADD/...
目标常量：
匹配结果：
最终函数地址：
```

同一哈希值可能碰撞，大小写、Unicode、模块名参与方式和终止符处理也会改变结果。只有当算法对一组已知 API 均能复现时，才应批量命名。

## 0x17 完整性校验与反调试的关系

壳可能校验自身代码、原始节、导入、调试寄存器或关键数据。断点、补丁、Dump 时机和页面权限变化都可能触发校验失败。应先识别“取值范围—计算算法—期望值—失败分支”，再决定使用不修改字节的观测方法或在副本上做最小实验。

更系统的反调试与反反调试方法放在下一篇笔记中。本篇只记录它对脱壳流程的影响：调试现场与正常运行现场可能不同，因此关键结论至少用第二种方式复核。

## 0x18 进程替换、子进程与映射执行

有些加载器不会在当前映像内恢复原程序，而是创建子进程、映射新的映像或把内容写入其他进程。此时当前模块的 OEP 不再是唯一目标，应跟踪“真实负载位于哪个进程、哪个映射、由哪个线程首次执行”。

- 记录父子进程关系、创建参数、挂起/恢复时机和入口线程。
- 比较远程写入区与磁盘 PE 的头、节和入口。
- 区分正常安装器/启动器行为与刻意隐藏的映射加载。
- 在新进程重新建立模块、线程、内存区域和 API 时间线。

## 0x19 差分分析

差分分析用于回答“壳在哪个阶段改变了什么”。可以比较磁盘与内存、执行前与执行后、不同输入、调试与非调试、成功与失败路径。

- 字节差分：定位解密块、补丁点和一次性数据。
- 页面差分：统计新增、删除、权限变化和私有化页面。
- 导入差分：比较模块与 API 集合何时出现。
- 控制流差分：比较相同入口在不同条件下的基本块轨迹。
- 行为差分：比较文件、注册表、网络和输出，但将行为证据与脱壳结构证据分开记录。

## 0x1A 自动化与可重复记录

自动化应服务于证据收集，而不是替代判断。适合自动化的内容包括 PE 字段快照、内存映射、页面哈希、模块导出反查、候选 IAT 扫描和多阶段差分。

```text
每次命中记录：
时间戳 / 进程 / 线程
RIP(EIP) / RSP(ESP)
模块+RVA
事件类型

寄存器摘要
调用栈

```

脚本输出应带版本、输入哈希、参数和错误信息。不要只保存一张截图，因为截图无法重放、搜索和批量对比。

## 0x1B 转储文件的验证矩阵

- 结构验证：PE 解析器能够读取头、节、目录和导入，无越界或重叠错误。
- 加载验证：系统加载器能够映射文件，入口和 TLS/异常结构有效。
- 功能验证：正常输入、错误输入和关键功能与原样本的可观察结果一致。
- 环境验证：重复启动、不同目录、不同基址或重启虚拟机后仍可运行。
- 静态验证：反汇编器能够建立合理函数、交叉引用和调用图。
- 差异解释：转储与原文件、未加壳真值之间的每类主要差异都有原因。

## 0x1C 常见失败与定位方法

- Dump 后立即崩溃：检查 OEP、IAT、TLS、重定位、异常目录和节权限。
- 只能在原调试会话运行：检查壳遗留状态、动态分配区、句柄、环境变量和未写入磁盘的数据。
- 导入修复后调用错位：检查 Thunk 边界、x86/x64 指针宽度、序号导入和误识别的普通指针。
- 静态工具反汇编混乱：确认代码字节是否稳定、节属性是否正确、入口是否落在真实指令边界。
- 断点总被跳过：检查新线程、异常转移、硬件断点线程归属、直接系统调用和子进程。
- 同一地址每次内容不同：考虑 ASLR、按需解密、随机化、运行时生成代码或多版本路径。

## 0x1D 常见误区

- 把查壳工具名称当成确认结论，不验证入口和运行时行为。
- 把第一次跨节跳转当成 OEP，忽略中间加载器和多层壳。
- 只改入口点，不检查导入、重定位、TLS 和异常信息。
- 直接用内存地址覆盖磁盘偏移，混淆 VA、RVA 与 FOA。
- 看到 RWX 就断言恶意或加壳，忽略 JIT、插件和普通运行库。
- 为追求“完全脱壳”耗费大量时间，却没有围绕分析问题确定最小恢复范围。
- 不保存失败现场，导致每次重新启动都重复相同试错。

## 0x1F 一次完整复盘应回答的问题

- 为什么判断样本存在壳，哪些证据只是弱特征？
- 壳在何处写入原始代码，目标区域经历了哪些权限变化？
- 如何证明候选位置是原程序边界，而不是中间 Stub？
- 转储时哪些运行时状态已经稳定，哪些仍依赖原壳？
- IAT、重定位、TLS、异常和安全目录分别如何处理？
- 修复后的文件通过了哪些结构和行为验证？
- 本次方法可迁移到哪些壳，哪些步骤只适用于当前样本？

## 0x20 资料与交叉验证

学习时可以把 PE/COFF 规范、Windows 加载器与虚拟内存文档作为结构基线，再用看雪论坛中的 UPX 手工脱壳、OEP 定位、IAT 修复、x64dbg 调试和虚拟化保护分析文章补充实战观察。论坛文章中的地址、插件界面和固定特征往往依赖样本与版本，应转化为可验证的方法，而不是直接背结论。

最有效的练习是建立自己的对照样本：保留未加壳文件，生成带壳副本，完整记录从静态差异到运行时恢复再到转储验证的全过程。存在真值时，才能判断 OEP、导入和修复结果是否真的正确。

## 0x21 总结

脱壳与壳分析的核心不是某个插件按钮，而是恢复时间线：壳从哪里开始，向哪里写入，何时把数据变成代码，如何解析外部依赖，怎样把控制权交给原程序。围绕“分配—写入—权限—导入—转移—验证”组织证据，再处理 OEP、IAT、重定位、TLS、异常和节结构，才能得到可复现、可继续逆向的结果。
