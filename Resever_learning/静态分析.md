# 静态分析

静态分析是在不执行目标程序的前提下，通过文件结构、机器码、字符串、符号、资源、交叉引用和控制流恢复程序模型。它适合快速建立全局地图、提出行为假设、选择动态断点位置，并为后续调试提供函数名、数据结构和地址坐标。

静态结果描述的是“文件和代码中存在什么”，不自动证明某条路径一定会执行。自动反编译、函数识别和类型推断都可能出错，因此关键结论必须回到原始字节、指令和交叉引用验证。

## 0x00 明确静态分析目标

打开样本前先写出问题。目标可以是寻找输入校验、定位配置解析、理解文件格式、恢复协议字段、识别算法、寻找崩溃相关代码或建立整体行为概览。问题越具体，静态分析越容易决定从哪里开始、何时停止。

```text
对象：sample.exe
问题：配置文件中的 server 字段如何进入连接函数？
入口线索：字符串 "server"、文件读取 API、网络 API
需要确认：解析函数、保存结构、调用路径、默认值
动态交接：在候选解析函数和 connect 调用点设置断点
```

## 0x01 样本基线与证据保全

- 计算 SHA-256，并记录文件大小、采集时间和来源说明。
- 只分析副本，原始样本设为只读并独立保存。
- 记录工具名称、版本、处理器架构和加载基址。
- 保存导入数据库、分析日志、脚本和重命名记录。
- 任何补丁都单独生成副本，记录原偏移、原字节和新字节。

哈希用于确认后续工具处理的是同一份文件。即使文件名相同，重新下载、解压或被工具修改后也可能成为不同样本。

## 0x02 初筛：先判断能否直接静态分析

- 文件格式与架构：PE32、PE32+、.NET、驱动、脚本或其他容器。
- 入口点与节权限：入口是否位于正常可执行区域。
- 导入数量：是否只保留少量加载和内存相关 API。
- 节名、节大小与熵：是否存在压缩、加密或异常映射迹象。
- 资源与 Overlay：是否嵌入配置、二级载荷、脚本或安装数据。
- 签名与调试信息：证书、PDB 路径、编译器和链接器线索。

高熵、少量导入、可写可执行节和异常入口点只是加壳候选特征。正常压缩资源、安装程序、JIT 或商业保护也可能出现相似现象，不能仅凭单一指标下结论。

## 0x03 工具分工

- 十六进制编辑器：查看原始偏移、签名、结构边界和未解析数据。
- PE-bear、CFF Explorer、DIE：快速查看 PE 头、节、目录、导入和壳特征。
- IDA、Ghidra、Binary Ninja：反汇编、反编译、交叉引用、图和类型恢复。
- strings、FLOSS：提取普通字符串和部分栈/解码字符串候选。
- capa、YARA：基于特征提出能力或分类候选，不能替代人工确认。
- Python、pefile、LIEF、Capstone：批量提取、校验和自动标注。

同一个结论尽量由两种视角支持。例如，工具显示某目录存在，还应验证目录 RVA、大小和所属节；规则匹配显示网络能力，还应找到实际调用点和参数来源。

## 0x04 字符串分析

字符串是静态分析最有效的入口之一，但字符串本身只表示字节存在。要证明用途，需要沿数据交叉引用找到引用代码，再继续追踪引用代码的调用者和条件分支。

- ASCII、UTF-8、UTF-16LE 等编码分别搜索。
- 关注格式串、错误文本、路径、注册表键、域名、协议常量和命令行选项。
- 区分直接引用、指针表引用、资源引用和运行时构造。
- 检查相邻字符串，常能发现同一功能模块的其他线索。
- 没有交叉引用的字符串可能属于资源、未使用代码、动态引用或误识别数据。

```text
字符串 "invalid license"
 -> 数据 Xref 到 show_error
 -> show_error 的调用者
 -> 调用前的 Jcc
 -> 条件使用的返回值
 -> 返回值来源函数
 -> 输入与比较逻辑
```

### 4.1 格式串是函数原型线索

printf、日志和格式化 API 的格式串能够提示后续参数数量和类型。例如 %s、%d、%p、%llx 可用于核对调用约定和变量宽度。格式串也可能由包装函数消费，因此应先确认最终调用目标。

## 0x05 导入表：能力索引而非行为结论

导入表可以快速显示程序依赖哪些 DLL 和 API。文件、注册表、网络、服务、加密、内存和进程相关 API 是很好的导航入口，但只有找到调用点、参数和实际路径后，才能判断用途。

- CreateFile/ReadFile：可能读取配置、资源、设备或普通数据。
- VirtualAlloc/VirtualProtect：可能用于正常内存管理、JIT、解压或自修改。
- LoadLibrary/GetProcAddress：可能是插件加载，也可能是动态解析。
- WinHttp/WinInet/Winsock：说明存在网络能力候选，不说明连接目标或是否执行。
- Crypt*/BCrypt*：说明使用系统加密接口，不说明具体业务语义。

导入表可能不完整：延迟导入、运行时解析、API Set、手工导出表解析和壳都会减少静态可见 API。反过来，导入存在也可能从未被调用。

## 0x06 导出、资源和调试信息

- 导出表：DLL 对外接口、序号导出、转发导出和潜在插件协议。
- 资源：图标、版本、Manifest、字符串表、对话框、嵌入文件和自定义资源。
- Debug Directory：PDB 路径、GUID、Age 和构建环境线索。
- Version Info：公司名、产品名和版本号属于元数据，可能被伪造。
- Manifest：执行级别、依赖程序集和兼容性声明。

资源内容需要按真实格式继续解析。发现 PNG、ZIP、脚本或另一个 PE 时，应记录资源类型、语言、RVA、大小和提取哈希，避免只保存一个脱离来源的文件。

## 0x07 入口点不等于 main

PE 的 AddressOfEntryPoint 通常进入运行库或初始化代码。真正的 main、WinMain、DllMain 或业务入口可能在 TLS、运行库启动函数和全局构造之后。壳的入口点更可能先执行解压和修复。

```text
PE EntryPoint
 -> 运行库初始化
 -> 安全 Cookie / 异常支持
 -> 全局构造与 TLS
 -> main / WinMain
 -> 用户业务逻辑
```

定位 main 时可结合运行库特征、命令行参数构造、退出函数调用和用户字符串交叉引用。不要把入口点函数直接重命名为 main，除非调用关系和参数语义已经确认。

## 0x08 反汇编与反编译的关系

反汇编展示处理器指令，反编译器根据控制流、数据流、调用约定和类型生成接近 C 的表达。伪代码是阅读工具，不是原始源码；错误的函数边界、栈变量、调用约定或类型都会向伪代码传播。

- 关键比较：回到 CMP/TEST、操作数宽度和 Jcc。
- 关键参数：回到调用点查看寄存器、栈和浮点参数。
- 关键字段：回到实际 [base+offset] 访问确认偏移。
- 关键循环：核对边界、计数器宽度和退出条件。
- 关键返回：确认返回寄存器、隐藏返回缓冲区或异常路径。

## 0x09 函数识别与边界修正

分析器通过调用目标、函数序言、异常展开信息、符号和控制流猜测函数边界。优化、尾调用、共享代码块、手写汇编、跳转表和混淆都可能造成误识别。

- 代码被识别成数据：检查真实控制流是否进入该区域。
- 函数被拆成多个函数：检查跳转和共享尾块。
- 多个函数被合并：检查多个合法入口和独立调用点。
- 尾调用被当成普通跳转：检查调用约定和栈状态。
- 跳转表未识别：检查索引范围、表项宽度和基址计算。

修正函数边界后应让工具重新分析，并检查交叉引用、调用图和伪代码是否同步改善。局部修正如果让更多内容变得矛盾，说明原假设可能错误。

## 0x0A 交叉引用：从线索扩展到关系

交叉引用分为代码引用和数据引用，可进一步区分调用、跳转、读取、写入和取地址。IDA 的 Xrefs、Cross References Tree 和图视图能够展示函数与数据之间的关系，但自动分析无法保证识别所有间接引用。

- Xrefs To：谁引用当前函数、字符串、全局变量或字段。
- Xrefs From：当前函数调用或访问了什么。
- 读取引用：寻找数据被消费的位置。
- 写入引用：寻找状态初始化和修改位置。
- 取地址引用：可能是回调注册、函数表、对象字段或间接调用。

```text
目标字符串/全局变量
 -> Xrefs To
 -> 候选函数
 -> 调用者层级
 -> 入口事件或用户操作

目标函数
 -> Xrefs From
 -> 子调用与数据依赖
 -> 外部副作用
```

### 10.1 间接调用没有天然 Xref

call rax、call [vtable+offset]、回调数组和哈希解析 API 的目标可能无法自动建立交叉引用。应通过函数指针的写入点、类型、表结构、导出解析和动态值补充关系。

## 0x0B 控制流图

控制流图以基本块为节点，以可能的执行转移为边。基本块内部顺序执行，末尾由条件跳转、无条件跳转、调用或返回决定后续路径。图视图适合观察分支和循环，但隐藏了部分数据细节，必要时切回线性视图。

- 入口块：函数开始或异常入口。
- 条件块：根据标志位或布尔表达式选择后继。
- 循环回边：从后续块返回前面的块。
- 汇合块：多条路径共享后续逻辑。
- 退出块：返回、抛出异常或尾调用。

颜色和图形布局是工具展示，不是程序语义。真正的条件要回到跳转指令和标志位；异常边、间接跳转和反编译器重构也可能不完全显示在普通 CFG 中。

## 0x0C 数据流：值从哪里来、到哪里去

数据流分析围绕定义、使用、传播和合并展开。逆向时常从一个关键值向前切片寻找来源，或向后切片寻找它影响的输出和分支。

```text
输入缓冲区
 -> 长度检查
 -> 解码/复制
 -> 结构字段
 -> 比较或计算
 -> 返回值/全局状态
 -> 后续分支
```

- 寄存器复用：同一个寄存器在不同时刻可能代表不同变量。
- 别名：两个指针可能指向同一内存，写入会互相影响。
- 类型转换：截断、符号扩展和零扩展会改变值域。
- SSA/Phi：反编译器可能把多个路径的值合并成一个逻辑变量。
- 内存状态：跨函数的结构字段和全局变量需要单独追踪写入点。

## 0x0D 从条件分支恢复判断逻辑

恢复判断逻辑时，不要只读伪代码中的 if。先确定 CMP/TEST 的操作数，再确认有符号或无符号跳转，最后追踪两个操作数的来源。

```asm
mov eax, [rcx+10h]
cmp eax, 100h
ja invalid_size
```

这段代码表示把对象偏移 0x10 的 32 位字段按无符号数与 0x100 比较，字段大于 0x100 时进入失败路径。字段是否真是 size，还需结合写入点、循环边界和后续使用确认。

## 0x0E 循环识别与边界检查

- 找初始化：计数器、指针和长度从哪里来。
- 找条件：进入循环前判断还是循环尾判断。
- 找步进：计数器增加多少，指针按多大元素移动。
- 找副作用：每轮写入什么、调用什么函数。
- 找退出：正常完成、提前 break、错误路径或异常。

安全相关分析尤其要核对长度类型、乘法溢出、符号转换和终止条件。反编译器显示的 int、unsigned 或 size_t 可能只是推断，应结合寄存器宽度和指令确认。

## 0x0F Switch、跳转表和状态机

switch 可能被编译为比较链、二分搜索或跳转表。跳转表通常包含范围检查、索引归一化、表项读取和间接跳转。状态机则可能在循环中根据状态值反复分派。

```asm
cmp eax, 7
ja default_case
lea rcx, jump_table
movsxd rax, dword ptr [rcx+rax*4]
add rax, rcx
jmp rax
```

混淆代码也常把正常控制流转换成状态机。区分正常编译 switch 与控制流平坦化，需要观察状态变量的写入规律、分支数量和每个 case 的真实副作用。

## 0x10 类型恢复

类型恢复能够显著改善伪代码，但类型应从访问方式逐步建立，而不是一次性猜测完整结构。先确定宽度和指针层级，再根据稳定偏移创建结构体，最后补充枚举、函数指针和嵌套类型。

- 1 字节访问：char、bool、标志或字节数组候选。
- 2/4/8 字节访问：整数、句柄、偏移或指针候选。
- 连续固定偏移：结构体字段候选。
- base + index * scale：数组或表。
- 首字段解引用后间接调用：C++ 虚表候选。
- 地址传给写入型 API：输出参数或缓冲区。

```c
struct Candidate {
    void *vtable;      // +0x00，候选
    uint32_t state;    // +0x08，多个写入点支持
    uint32_t length;   // +0x0C，用于循环上界
    uint8_t *buffer;   // +0x10，传入读取/复制函数
};
```

字段名应体现证据强度。初期使用 field_10、candidate_length、possible_callback，待调用语义、读写点和动态值确认后再改成业务名称。

## 0x11 函数原型恢复

- 从调用约定确定参数位置和易失/非易失寄存器。
- 从调用点统计稳定传入的参数数量。
- 从函数内部观察参数读取宽度和解引用方式。
- 从返回路径判断返回寄存器和错误码语义。
- 从多个调用点对比 NULL、常量、缓冲区和对象参数。
- 识别隐藏 this 指针和结构体返回缓冲区。

函数调用点是恢复原型的重要证据。单独阅读函数内部可能把全局变量误认为参数，也可能忽略调用者在栈上准备的附加参数。

## 0x12 C++ 静态分析

C++ 二进制中需要额外关注名称修饰、构造析构、虚表、RTTI、异常和模板实例。编译器优化可能内联小函数、合并相同实现或删除未使用类型信息。

- 构造函数：常写入 vtable 并初始化字段。
- 析构函数：释放成员资源，可能恢复基类 vtable。
- 虚调用：对象取 vtable，再从固定槽位间接调用。
- RTTI：可辅助恢复类继承，但可能被剥离或关闭。
- this 调整 thunk：多重继承时可能先调整对象指针再跳转。

## 0x13 全局变量与初始化

全局变量的语义通常由写入点比读取点更容易确认。先找零值或常量初始化，再找运行时更新，最后看哪些函数读取它决定行为。全局构造、TLS 和延迟初始化会使状态在 main 前或首次使用时建立。

## 0x14 库函数与编译器代码

静态分析数据库通常会识别运行库和已知库函数。把库代码与业务代码区分开，可以减少阅读量，但识别结果可能受静态链接、优化和版本影响。

- 常见 memcpy/memset 可能被内联成向量化循环。
- 字符串和容器操作可能展开为大量模板代码。
- 安全 Cookie、异常展开和 CFG 检查属于编译器插入逻辑。
- 函数签名匹配只能作为候选，关键调用仍需核对。

## 0x15 常量与算法线索

魔数、轮常量、S-box、协议头和多项式可以帮助识别算法，但常量重复、变形实现和编译优化都会造成误判。识别后应验证数据宽度、轮数、输入输出和调用上下文。

- 加密候选：固定轮常量、密钥扩展、查表和密集位运算。
- 校验候选：循环处理输入并更新小型状态，最终比较或输出。
- 压缩候选：位流读取、滑动窗口、频率表和大量边界处理。
- 编码候选：固定字母表、分组位移和填充规则。

## 0x16 静态分析加壳样本时的边界

若入口主要执行解压、解密、权限修改和间接跳转，磁盘静态分析通常只能解释壳逻辑。此时应记录壳入口、内存分配、写入范围、IAT 修复和最终跳转候选，把后续工作交给动态分析与内存转储。

不要在壳代码中无限追踪每个循环。静态阶段的目标是找到解包阶段边界和可观察事件，例如新可执行内存、模块解析、导入修复或跳往新区域。

## 0x17 注释和命名规范

- 函数：按动作和对象命名，例如 parse_config、candidate_decrypt_block。
- 变量：表达数据含义和证据强度，避免 var1、temp2 长期保留。
- 地址：长期记录 module+RVA，文件数据记录 FOA 和长度。
- 注释：写“为什么”和证据，不要重复指令表面语义。
- 颜色/书签：建立统一规则，例如红色待验证、绿色已确认。

```text
差的注释：eax 加 1
好的注释：索引前进到下一条 24 字节记录；上界来自 header.count

差的命名：decrypt_data
谨慎命名：candidate_transform_buffer
确认后命名：aes_cbc_decrypt_payload
```

## 0x18 IDA 数据库操作流程

建议先等待自动分析完成，再从 Imports、Strings、Functions 和 Segments 建立入口列表。图视图用于理解基本块和边，线性视图用于核对连续字节和数据；交叉引用树适合浏览函数与数据关系。重命名和类型修改会传播到伪代码，因此每次修改后都应观察整体结果是否更一致。

- 保存关键位置书签，而不是依赖导航历史。
- 修正函数边界后重新检查 callers/callees。
- 创建 Local Types，逐步应用到参数、局部变量和全局对象。
- 对重要修改记录依据，避免数据库后期无法追溯。
- 定期保存数据库副本，防止错误类型传播到大量函数。

## 0x19 自动化与 IDAPython

重复性的枚举、搜索、重命名和导出工作适合脚本化。脚本应输出稳定标识和日志，并对数据库修改提供预览或白名单，避免自动错误扩散。

```python
import idautils
import ida_funcs

for ea in idautils.Functions():
    f = ida_funcs.get_func(ea)
    print(hex(ea), ida_funcs.get_func_name(ea), hex(f.end_ea - f.start_ea))
```

- 批量导出函数、字符串和交叉引用。
- 查找调用某组 API 的函数。
- 按指令或常量模式标记候选函数。
- 将 module+RVA 和命名导出为 JSON。
- 比较两个版本中函数大小、哈希和调用关系变化。

## 0x1A 版本差异分析

对同一程序的两个版本进行比较，可以快速定位新增功能、修复逻辑和结构变化。优先使用稳定特征：调用关系、字符串、常量、基本块结构和类型，而不是绝对地址。

- 确认两个文件的架构、编译模式和保护方式是否相近。
- 匹配入口、导出、字符串和已知函数。
- 比较函数图、指令序列和调用者变化。
- 将差异分为编译噪声、布局变化和真实逻辑变化。
- 对关键差异回到动态测试验证。

## 0x1C 综合实战流程

- 第一轮：记录哈希、架构、节、入口、导入、资源和保护特征。
- 第二轮：从字符串、导入和导出建立功能入口列表。
- 第三轮：沿交叉引用恢复主要调用链。
- 第四轮：阅读关键函数的 CFG 和数据流，修正边界与类型。
- 第五轮：形成结构体、函数原型和行为假设。
- 第六轮：生成动态断点列表与最小测试输入。
- 第七轮：根据动态结果回填静态数据库并完成复盘。

## 0x1D 常见错误

- 把工具自动命名当成事实。
- 只看伪代码，不核对汇编和操作数宽度。
- 字符串一出现就直接推断行为。
- 导入 API 存在就认为一定调用。
- 把所有间接调用都忽略，导致调用图断裂。
- 过早恢复完整结构体，使错误类型传播。
- 只记录绝对地址，不记录模块和 RVA。
- 在明显加壳样本中无限阅读壳循环。
- 修改数据库后不记录依据，后续无法区分工具结果和人工推断。

## 0x20 总结

静态分析的核心是建立可验证的关系：字节属于什么结构，函数由谁调用，数据从哪里写入，条件如何控制路径，类型依据是什么。字符串和导入帮助找到入口，交叉引用连接关系，控制流解释路径，数据流解释值，类型恢复让模型逐渐接近程序真实结构。最终成果应能够明确告诉动态分析：在哪里断、观察什么、用什么输入以及哪条假设需要被证实。
