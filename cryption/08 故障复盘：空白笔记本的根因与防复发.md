# 08 故障复盘：空白笔记本的根因与防复发

# 故障复盘：cryption 笔记本空白的真正原因

## 0x00 撤回上次误诊

之前将空白归因于 sort.json 缺少登记，并宣称已修复，这个结论缺少应用层证据。sort.json 是排序元数据，不是有效文档与块索引的替代品。本次在 sort.json 已登记九项的情况下，listDocsByPath 和 SQL 仍只返回一个未命名空白文档，直接否定“补排序就修复”的结论。

## 0x01 实际证据

原文件名如 20261009210000-aes.sy、20261009210000-index.sy，后缀不是七位小写字母数字；上次新增复盘的 index-repair 也一样非法。getBlockInfo 对原 AES ID 返回 code=-1、msg=invalid ID argument。还存在 li000299、oi000314 等八位节点后缀，且 NodeListItem 直接挂在文档下，没有 NodeList 容器。

## 0x02 修复方式

保留原始文件及 SHA-256，把正文与代码转成 Markdown，再调用当前运行的思源 createDocWithMd。由思源生成合法 ID、列表树与块索引。保留用户新建的空白文档；旧非法文件在新文档逐篇回读成功后归档备份。没有重建整个工作区、删除数据库或覆盖用户笔记。

## 0x03 验收门槛

文件存在、JSON 可解析、Python 编译成功都不代表笔记可见。必须检查 listDocsByPath 返回文档 ID；getBlockInfo 返回 code=0；getDoc 返回 code=0 且正文非空；SQL 能查到文档块；每篇内容中的 Python 代码块与原脚本一致。进一步检查应用生成的所有 ID 合法、NodeListItem 的父节点是 NodeList。

## 0x04 防复发

优先使用思源 Markdown API 创建和更新笔记，不手写正在使用中的 .sy 文档。生成操作保存创建 ID，重试按记录去重。旧生成器停用并替换为可重复执行的应用层验证入口。将这次教训同步到本地 Codex 知识记录；不能只把经验写进又一篇非法 ID 的不可见笔记。
